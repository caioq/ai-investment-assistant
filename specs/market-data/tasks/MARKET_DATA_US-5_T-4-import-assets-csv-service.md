# MARKET_DATA_US-5_T-4: MarketDataService.importAssetsCsv

Add `MarketDataService.importAssetsCsv(csvText: string): Promise<{ created: number; updated: number; errors: string[] }>` (`apps/api/src/market-data/market-data.service.ts`), the sole writer of `Asset.sector`/`subSector`/`investmentStyle`/`riskRating`.

Follow the **partial-success** pattern from `PortfolioService.importHoldingsCsv`, not `validateWalletRows`' whole-file rejection (`CONVENTIONS.md` → "CSV parsing" documents both and when each applies): process each row independently in a loop, wrap `normalizeAssetRow` in a try/catch, and collect failures as `row N: reason` strings in `errors[]` without aborting or rolling back the rows that succeeded.

Behavior, all from the spec:

- **A row with an empty `ticker` is skipped silently** — not counted in `created`/`updated`, and **not** added to `errors[]`. The source sheets end in spreadsheet furniture, and reporting those as failures would show ten errors on a good file.
- **Resolve the ticker with `findOrCreateAsset`** (`CONVENTIONS.md` → "Find-or-create master data"), never a bespoke `findUnique`-then-`create` — it owns the uppercase rule and the P2002 race recovery, both of which were expensive to get right. Its `wasCreated` flag is what distinguishes `created` from `updated` in the response. Unlike `portfolio`, this caller must **not** trigger `backfillHistory` on `wasCreated: true`: classifying a ticker is not the same as taking a position in it, and firing a year of history fetches for every row of a large assets CSV would hammer the upstream this module exists to protect.
- **Apply only the keys `normalizeAssetRow` returned.** A key absent from its result must not appear in the Prisma `update` data at all (leave the stored value alone); a key present as `null` must be written as `null` (clear it). Building the update object from a fixed six-key literal defeats the whole absent-vs-empty rule — construct it from the normalised row's own keys.
- A ticker whose row fails normalisation must leave that asset's **existing** stored classification untouched — validate the row before writing anything for it, don't partially apply then throw.

**Test:** `apps/api/test/market-data-assets-import.e2e-spec.ts` — a new e2e spec (real Postgres, per `CONVENTIONS.md` → "Testing"), reading the `MARKET_DATA_US-5_T-1` fixtures, with an `afterEach` scoped to `where: { ticker: { in: [...] } }` for this suite's `MDAS*` tickers only — never an unscoped `deleteMany()`, which races the other suites sharing the test database. Asserts: (1) importing `assets-full.csv` into an empty table creates one `Asset` per non-empty-`ticker` row with all four classification fields stored, `created` equal to that count and `errors` empty — including a ticker that has no `Holding` and no `RecommendedHolding`, which is the spec AC no other upload path can satisfy; (2) the empty-`ticker` row produced neither an `Asset` nor an `errors[]` entry; (3) the `ETF` row stored `investmentStyle: ETF`; (4) re-importing with a changed `riskRating` reports it under `updated` (not `created`) and overwrites the stored value; (5) importing `assets-partial.csv` afterwards leaves `investmentStyle`/`riskRating`/`assetType` at their previously stored values (absent column ⇒ untouched); (6) importing `assets-empty-cells.csv` sets that row's `riskRating` to `null` (empty cell ⇒ cleared) — (5) and (6) together are the pair that would both pass against a buggy implementation if only one were written; (7) `assets-bad-values.csv` reports two `errors[]` entries naming rows and reasons, still imports the valid rows, and leaves the bad rows' pre-existing classification unchanged; (8) running `refreshAllQuotes()` (with `PRICE_PROVIDER` stubbed, as `market-data.e2e-spec.ts` already does) after an import updates `currentPrice` but leaves all four classification fields exactly as imported — the price-cron half of the spec AC "Neither the price cron nor a recommended-portfolios wallet upload ever writes…", whose wallet half is already guarded by `apps/api/test/recommended-portfolios.e2e-spec.ts`.
