# `apps/web/e2e/`

Playwright end-to-end + visual-regression specs for the web app, one spec
per critical user flow (`CONVENTIONS.md` -> "Testing"). Run locally with
`pnpm --filter web test:e2e`; see `../playwright.config.ts` for the two
`webServer` entries (API on `3001`, web app on `3000`, both pointed at
`db-test`) and `./global-setup.ts` for the fixture users this suite logs in
as.

| Spec | Covers |
| --- | --- |
| `auth.spec.ts` | Unauthenticated redirect, login, logout, auth-guard round trip through a real browser and real cookie. |
| `dashboard-visual.spec.ts` | Visual regression: the populated and empty dashboard against their own committed baselines. See below. |

## Visual regression (`dashboard-visual.spec.ts`)

**What this checks, and what it deliberately doesn't.** This spec compares
the rendered dashboard against **its own previously committed
screenshot**, never against
[`resources/UI/portfolio-dashboard.html`](../../../resources/UI/portfolio-dashboard.html)
— that file is a declarative prototype (its own `support.js` runtime,
hardcoded demo data) that this app deliberately doesn't reproduce
byte-for-byte, so a diff against it would fail by design. See
`specs/dashboard-ui/spec.md`'s Non-Goals for the full rationale. What this
check catches is *"the dashboard still looks like it did yesterday"* —
genuinely useful, and a different claim from *"the dashboard matches the
mockup"*, which is a human-review judgment made once, when a baseline is
first approved.

**Determinism.** The populated screenshot logs in as
`VISUAL_REGRESSION_POPULATED_USER` (`./fixtures/visual-regression-users.ts`),
seeded with a fixed set of holdings, portfolio-value/benchmark snapshots,
and one advisor analysis, written directly via a plain `pg` client rather
than through the live API — see `./fixtures/visual-regression-seed.ts`'s
doc comment for why (`POST /portfolio/holdings` would otherwise reach out
to the real, rate-limited, non-deterministic Yahoo Finance endpoint). The
advisor panel's "Generated by ... " footer is additionally `mask:`ed in the
screenshot assertion, since its date is formatted through the local
timezone even though the underlying `createdAt` is fixed. The empty
screenshot logs in as a separate, never-seeded `VISUAL_REGRESSION_EMPTY_USER`
so the two screenshots never depend on run ordering within the suite.

### Baselines are platform-specific — read this before regenerating one

Font rasterisation and scrollbar metrics differ between macOS/Windows and
Linux. A baseline generated on a contributor's laptop will fail on **every**
CI run with a diff that looks like nothing changed to a human eye — CI runs
on Linux (a GitHub Actions Ubuntu runner, see `DASHBOARD_UI_SHARED_T-8`),
and Playwright's screenshot comparison is exact-pixel, not perceptual.

**Local baselines MUST be generated/updated inside the
`mcr.microsoft.com/playwright:v1.63.0-jammy` container** — the version tag
matches `@playwright/test`'s version in `apps/web/package.json`
(`"@playwright/test": "^1.63.0"`); bump both together if that dependency is
ever upgraded, since a mismatched browser/runner pair can silently rasterise
differently.

**CI does *not* use this container.** `DASHBOARD_UI_SHARED_T-8`'s CI job
already runs Playwright natively on the GitHub Actions Ubuntu runner, which
is itself a consistent Linux environment — the same one a `jammy`-container
run on a non-Linux dev machine reproduces. This container is purely a local
convenience so a macOS/Windows contributor's baseline run rasterises
identically to what CI will compare it against; CI needs no container of
its own since it's already Linux.

#### The exact command

1. Make sure `db-test` is up on the host first (the containerized run below
   reaches it over the host's own network, not a container network — see
   the networking note below):

   ```sh
   docker compose up -d db-test
   ```

2. From the repo root, run the whole suite (or just this spec) inside the
   container with `--update-snapshots`:

   ```sh
   docker run --rm -it \
     --network host \
     -v "$(pwd)":/work -w /work \
     mcr.microsoft.com/playwright:v1.63.0-jammy \
     bash -c "corepack enable && pnpm install --frozen-lockfile && CI=true pnpm --filter web test:e2e -- dashboard-visual.spec.ts --update-snapshots"
   ```

   Drop the `dashboard-visual.spec.ts` argument to regenerate every spec's
   baselines/traces, not just this one. `CI=true` is set deliberately: it's
   what makes `playwright.config.ts` use `reuseExistingServer: false` (so
   the container always boots its own API/web servers against `db-test`
   rather than trying to reuse a host-side `pnpm dev`, which it can't see
   through `--network host` port-forwarding assumptions anyway) and the
   HTML reporter.

   New/changed baseline `.png` files land under `apps/web/e2e/`
   (Playwright's default `__screenshots__`-style path next to the spec,
   scoped by project name) — review the diff, then commit them like any
   other file.

**Why `--network host`, not port-mapping or `host.docker.internal`.**
`docker-compose.yml`'s `db-test` service is only published to the **host's**
`localhost:5433` — there is no separate Docker network it and this
throwaway container both join. `--network host` makes the container share
the host's network namespace outright, so every `localhost` reference
already hardcoded in this harness (`./global-setup.ts`'s
`TEST_DATABASE_URL`, `playwright.config.ts`'s `webServer.url` healthchecks
and the API's own `DATABASE_URL`) resolves exactly as it does outside the
container, with zero code changes needed to run it there.

- **Linux (native Docker Engine, including a Linux dev machine or VM):**
  works exactly as shown above — `--network host` is fully supported and
  behaves identically to running the command directly on the host.
- **macOS / Windows (Docker Desktop):** `--network host` requires Docker
  Desktop's "host networking" support to be enabled (Settings -> Resources
  -> Network -> "Enable host networking"); without it, the flag is silently
  ignored and the container can't reach `db-test` on the host at all (every
  `localhost:5433`/`:3000`/`:3001` connection inside the container will
  simply refuse). If that setting isn't available in your Docker Desktop
  version, run the command from a Linux VM/devcontainer instead of trying
  to route around it with `host.docker.internal` — this harness's `pg`
  connection strings and `webServer` healthcheck URLs are hardcoded to
  `localhost`, not read from an env var, so there is no lower-effort
  alternative that doesn't also mean patching those files.

**One more gotcha:** installing dependencies *inside* the container writes
Linux-built native modules (e.g. `@next/swc`, `esbuild`) into the repo's
(mounted, shared) `node_modules`. Re-run `pnpm install` on the host
afterwards before going back to local `pnpm dev`/`pnpm test` outside the
container, or do baseline regeneration from a disposable worktree/clone
instead of your main working tree.

#### Demonstrating red

Per the task's own requirement (mirroring `DASHBOARD_UI_SHARED_T-8`'s CI
demonstration): a deliberate one-line CSS change (e.g. a changed `gap` or
`padding` in one of the `components/dashboard/*` files) should fail this
check with a visible diff image in the uploaded CI artifact
(`playwright-report/`, see `CONVENTIONS.md` -> "CI (GitHub Actions)"),
proving the check actually catches drift rather than being green
unconditionally. Revert the deliberate change afterward — it's a
demonstration, not a real fix.
