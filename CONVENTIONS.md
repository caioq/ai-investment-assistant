# Conventions

Living map of established patterns and reusable pieces in this codebase. Read this before implementing a task, so architecture doesn't need to be rediscovered by scanning the whole repo. Updated incrementally: whenever a task introduces a new reusable pattern, model, or utility, add a short entry here before marking that task `Done`. Keep entries short — a pointer (file path + one line), not a tutorial. Delete a placeholder heading's `<...>` note once real content exists under it.

## Backend (`apps/api`)

### Module structure
- One module per domain under `apps/api/src/<name>/` (`auth/`, `portfolio/`, `market-data/`, `advisor/`), each with `<name>.module.ts`, `<name>.controller.ts`, `<name>.service.ts`, and a `dto/` subfolder.
- Controllers stay thin: request/response shaping and calling into services only. Business logic (allocation math, prompt building, price aggregation, etc.) lives in services — or in `packages/shared` if it's pure logic the frontend also needs.
- All controller inputs are validated with `class-validator` DTOs behind a single global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true`) registered once in `main.ts` — no ad hoc manual validation inside individual controllers.
- `PrismaService` lives in a global `PrismaModule` (`apps/api/src/prisma/`), injected via constructor DI wherever a service needs DB access. Nothing instantiates `PrismaClient` directly. `PrismaModule` is `@Global()` and exports `PrismaService`, so downstream feature modules just inject it without re-importing `PrismaModule` (except a module with its own standalone `*.module.spec.ts` compiling it in isolation — see "Testing" below). `PrismaService extends PrismaClient`, connecting in `onModuleInit`/disconnecting in `onModuleDestroy`; Prisma 7's generated client requires an explicit driver adapter (no implicit binary engine), so the constructor passes `new PrismaPg({ connectionString: process.env.DATABASE_URL })` (`@prisma/adapter-pg` + `pg`, both added as `apps/api` deps). Since `apps/api/generated/prisma` is gitignored, `apps/api/package.json`'s `prebuild` and `pretest:e2e` scripts both run `prisma generate` first (also exposed standalone as `db:generate`) so a fresh checkout's `build`/`test:e2e` work without a manual step.
- Cross-cutting `INestApplication` config (CORS, global pipes, etc.) that both the real bootstrap and e2e tests need lives in `apps/api/src/configure-app.ts` (`export function configureApp(app: INestApplication)`), called from `main.ts`'s `bootstrap()` right after `NestFactory.create`. e2e specs import `configureApp` from `./configure-app`, never from `../src/main` directly — `main.ts` has a top-level, unconditional `bootstrap()` call, so importing it as a module (even just for a named export) triggers a real `NestFactory.create` + `app.listen()` as a side effect, leaving an open server handle that hangs the Jest process after the suite reports pass. See `apps/api/test/cors.e2e-spec.ts` for the pattern (sets `process.env.FRONTEND_URL` in `beforeAll`, then calls `configureApp(app)` between `createNestApplication()` and `.init()`).
- Prisma schema at `apps/api/prisma/schema.prisma` (datasource/generator only until a module adds models); `apps/api/prisma.config.ts` (Prisma 7) reads `DATABASE_URL` from `apps/api/.env` (gitignored, not committed — matches the `db` service in root `docker-compose.yml`: `postgresql://postgres:postgres@localhost:5432/investment_assistant?schema=public`). Root `pnpm db:migrate` proxies to `apps/api`'s own `db:migrate` script (`prisma migrate dev`), which needs `db` (from `docker-compose.yml`) up first.
- Every Prisma model gets an explicit `@@map("<snake_case_plural>")` so the physical table name is a lowercase plural (`users`, not Prisma's default PascalCase singular `User`) even though the model name itself stays PascalCase singular per Prisma convention. The same `snake_case` rule applies at the column level: any multi-word field gets `@map("snake_case_name")` (e.g. `passwordHash String @map("password_hash")`) — Prisma model field names stay camelCase (matching the rest of the TS stack), but the physical Postgres columns are `snake_case`. This isn't just style: unquoted camelCase identifiers get silently lowercase-folded by Postgres, so raw SQL, `psql`, migrations inspection, and any non-Prisma tool touching the DB directly need exact-case double-quoting to work at all — `snake_case` columns avoid that footgun entirely and match what virtually every non-Prisma SQL/BI tool assumes by default. See `User` in `apps/api/prisma/schema.prisma` (first model in the repo, added by `AUTH_US-1_T-1`) for the pattern.
- When a service needs to depend on an **interface** rather than a concrete implementation (so a future alternate implementation can be swapped in without touching the consumer), TS interfaces don't survive to runtime — Nest DI needs an explicit `Symbol` injection token exported alongside the interface, e.g. `export const PRICE_PROVIDER = Symbol('PRICE_PROVIDER')` next to the `PriceProvider` interface in `apps/api/src/market-data/providers/price-provider.interface.ts`. The module binds a concrete class to that token (`{ provide: PRICE_PROVIDER, useExisting: B3YahooProvider }` in `market-data.module.ts`), and the consumer injects via `@Inject(PRICE_PROVIDER) private readonly x: PriceProvider` rather than naming the concrete class — see `MarketDataService` (`MARKET_DATA_SHARED_T-2`).
- **Variant for a third-party SDK client that already satisfies a narrow interface structurally:** no wrapping `@Injectable()` class is needed — bind a plain `Provider` object literal with `useFactory` directly to the token. See `ANTHROPIC_CLIENT`/`AnthropicClient` (`apps/api/src/advisor/providers/anthropic-client.interface.ts` + `anthropic-client.provider.ts`, `ADVISOR_US-2_T-1`): the interface declares only the one SDK call the module makes (`messages.create`, typed with the SDK's own `MessageCreateParamsNonStreaming`/`Message` rather than redefined types), and `anthropicClientProvider`'s `useFactory` reads `process.env.ANTHROPIC_API_KEY` and throws a clear error naming the variable if it's absent, so a misconfigured deploy fails at boot (same `process.env`-direct pattern as `JWT_SECRET`, see "Auth" below) rather than at the first request. A test injects `{ messages: { create: jest.fn() } }` in place of the token — never a real `Anthropic` instance.
- Primary keys are UUIDv7, not autoincrementing integers or `cuid()`: `id String @id @default(uuid(7)) @db.Uuid`. Rationale — sequential integer ids are enumerable/guessable (a real risk once an id can end up in a URL, error message, or JWT payload); UUIDv7 is non-enumerable, globally unique without a DB round-trip, and (unlike random UUIDv4) still time-ordered, so it doesn't fragment the primary-key btree index the way v4 would at scale. `@db.Uuid` stores it as Postgres's native 16-byte `uuid` type (format-validated at the DB level) rather than Prisma's default `TEXT` mapping for `String` ids. Note the id is generated by Prisma Client itself (not a DB-level `DEFAULT`) — there's no `gen_random_uuid()`/`uuidv7()` in the migration SQL, since Postgres only gained a native `uuidv7()` function in v18 and this repo runs Postgres 16 (`docker-compose.yml`). This means a row's `id` only gets populated when inserted through Prisma Client — never via raw SQL/seed scripts that bypass it.
- To normalize a DTO string before validating it (e.g. trim so `"   "` fails `@IsNotEmpty()`), put `@Transform(({ value }) => typeof value === 'string' ? value.trim() : value)` (`class-transformer`) above the validators. The global pipe has no `transform: true`, but because validator options are set it still hands the controller the transformed instance, so the handler receives the trimmed value too. See `RegisterDto.name` (`apps/api/src/auth/dto/register.dto.ts`, `AUTH_UI_US-2_T-1`).

### Find-or-create master data
- `MarketDataService.findOrCreateAsset(ticker: string): Promise<{ asset: Asset; wasCreated: boolean }>` (`apps/api/src/market-data/market-data.service.ts`, `RECOMMENDED_PORTFOLIOS_US-1_T-5`) is the one place that finds-or-creates an `Asset` by ticker — uppercase-normalised, with P2002 race recovery (two concurrent requests for the same brand-new ticker both see `null`, both `create`, one loses and re-reads the winner's row instead of surfacing a 500). Any module that needs to resolve a ticker to an `Asset` (e.g. `portfolio`'s `upsertHolding`, which calls this instead of keeping its own copy) should call this rather than reimplementing it — the uppercase rule and the race recovery are both easy to get wrong and were expensive to find the first time. The caller decides what `wasCreated: true` should trigger (e.g. `portfolio` backfills 1y of history; `recommended-portfolios` and `MarketDataService.importAssetsCsv` (`MARKET_DATA_US-5_T-4`) deliberately do not — see each module's spec Behavior Notes), since that decision differs per caller.

### Cross-module summary endpoint (compose services, never re-query another module's tables)
- `DataSourcesService.getSummary(userId)` (`apps/api/src/data-sources/data-sources.service.ts`, `DATA_SOURCES_SHARED_T-5`) is the reference for one endpoint that needs a slice of data from several other modules' tables at once — it imports `MarketDataModule`/`PortfolioModule`/`RecommendedPortfoliosModule`/`AdvisorModule` and calls each module's own service (`MarketDataService.getAssetsSummary`, `PortfolioService.listHoldings`, `RecommendedPortfoliosService.getLatestPerWallet`, `AdvisorService.getLatestReport`) rather than querying `Asset`/`Holding`/`RecommendedPortfolio`/`AdvisorReport` directly, per the one-way module-boundary rule `market-data`'s spec states (also followed by `advisor`'s `gatherPromptContext`). Two of those service methods (`MarketDataService.getAssetsSummary`, `AdvisorService.getLatestReport`) didn't exist before this task and were added to the *owning* module rather than queried around — add the missing method to the module that owns the table, don't reach past it just because it's a one-line Prisma call. The four calls run via `Promise.all` since none depend on each other's result. `Asset` rows are global (spec's "Data ownership"), so `assets.count`/`tickers`/`lastImportAt` are the one section of the response not scoped to `userId` — its `ImportLog` lookup omits the `userId` filter the `holdings`/`wallets` sections use, on purpose.

### CSV parsing
- Use `csv-parse` (`csv-parse/sync`'s `parse()`), never `split(',')` — a `name` field or a Brazilian decimal comma silently shifts every column with naive splitting. Parse with `columns: false` (raw string arrays, not the `columns: true` object mode) plus `relax_column_count: true` so a wrong-column-count row doesn't throw and abort the whole parse — `columns: true` + `relax_column_count` silently drops extra columns instead of letting you catch and report a malformed row, whereas array mode lets each row's `.length` be checked explicitly against the expected count. `skip_empty_lines: true` drops a blank trailing line (a text-editor artifact, not a user mistake) without it becoming a reported error. See `PortfolioService.importHoldingsCsv` (`apps/api/src/portfolio/portfolio.service.ts`, `PORTFOLIO_US-2_T-1`) for the pattern: process each data row independently in a loop, collecting per-row failures into an `errors[]` array with a `row N: reason` message rather than throwing on the first bad row or wrapping the batch in one transaction — a malformed row must not roll back the good ones (spec AC-3).
- Brazilian-formatted numbers from a research-house export (`"R$ 40,99"`, `"8,00%"`, `"-6,71%"`, `"R$ 1.234,56"`) are parsed with `parseBrazilianNumber` (`apps/api/src/recommended-portfolios/brazilian-number.ts`, `RECOMMENDED_PORTFOLIOS_US-1_T-1`), never `Number()` — `Number("8,00%")` is `NaN`. It returns three distinguishable outcomes: a `number`, `null` for an absent value (empty/whitespace/`undefined` — never `0`, which is itself a valid published value), and `NaN` for a present-but-non-numeric value so a caller can reject the row instead of storing a silent `null`. A `.` is only stripped as a thousands separator when it groups digits in threes, so a stray en-US `"12.5"` can't become `125`.
- A row-level mapping function (a `RawWalletRow` → a persistable shape) throws on a value it can't map, rather than returning a silent `null` or a result object with an error field — see `normalizeWalletRow` (`apps/api/src/recommended-portfolios/wallet-row.ts`, `RECOMMENDED_PORTFOLIOS_US-1_T-3`), which throws on an unrecognised `RECOMENDACAO`. This keeps the mapper itself simple (a straight-line function, no error-accumulator threaded through it) and composes with the "CSV parsing" per-row `errors[]` pattern above: the whole-file validator (`RECOMMENDED_PORTFOLIOS_US-1_T-4`) wraps each row's call in the same try/catch it already uses to catch a malformed row.
- **An absent-vs-empty column distinction survives into the Prisma write by building `data` from the normalizer's own returned keys, not a fixed field list.** `normalizeAssetRow` (`apps/api/src/market-data/asset-row.ts`, `MARKET_DATA_US-5_T-3`) omits a key entirely when its CSV column was absent (leave untouched) but returns it as `null` when the column was present-but-empty (clear it) — see `MarketDataService.importAssetsCsv` (`market-data.service.ts`, `MARKET_DATA_US-5_T-4`), which destructures `{ ticker, ...updateData }` off the normalized row and passes `updateData` straight to `prisma.asset.update`. Hand-listing the six classification fields in the update call instead would defeat the whole point — every field would always be present in `data`, so "absent column" and "empty cell" would collapse into the same outcome.
- **Whole-file rejection is a different, equally valid CSV pattern from `importHoldingsCsv`'s partial-success one above** — pick it when the file is a *set* that only means something whole (a wallet snapshot), not a bag of independent rows (holdings). See `validateWalletRows` (`apps/api/src/recommended-portfolios/wallet-validation.ts`, `RECOMMENDED_PORTFOLIOS_US-1_T-4`): it collects every row's `row N: reason` failures (both its own field checks — a `targetWeightPct` out of `0`–`100`, a `NaN` from `parseBrazilianNumber`, an empty `label` — and `normalizeWalletRow`'s per-row throw, caught in the same loop) into one array, but never calls Prisma itself; it either throws one `BadRequestException` naming every bad row or returns every normalised row for the caller to persist in a single write. `RecommendedPortfoliosService.uploadWallet` calls this *before* any `prisma.recommendedPortfolio.create`, so a bad row anywhere in the file is caught with zero partial writes — never validate row-by-row interleaved with row-by-row inserts, which can leave a partial wallet behind even when the final error message is correct.

### Import history (`ImportLog`)
- `apps/api/src/data-sources/` (`DATA_SOURCES_SHARED_T-4`) owns the `ImportLog` model (`import_logs`, `ImportSource`/`ImportStatus` enums, `errors Json?` holding the rejected rows verbatim) and `GET|POST /data-sources/imports`, both `AuthGuard`-scoped to `req.user.id`. Any UI that finishes an upload writes its own log row here rather than each importer writing one server-side — an absent `errors` stays `Prisma.DbNull`, so "no rejected rows" and "errors not recorded" stay distinguishable.
- A numeric query param (e.g. `?limit=`) is coerced with `@Transform(({ value }) => Number(value))` before `@IsInt()` in its query DTO (`apps/api/src/data-sources/dto/list-imports-query.dto.ts`) — the global `ValidationPipe` has no `transform: true`, so a raw query string would otherwise always fail `@IsInt`.

### File uploads (`@nestjs/platform-express`)
- A multipart file-upload endpoint uses `@UseInterceptors(FileInterceptor('file', { limits: { fileSize: <bytes> } }))` with Nest's default in-memory storage (no `dest`/disk storage) when the file is parsed immediately and never needs to persist — the handler reads `file.buffer` and never touches disk. Always set `limits.fileSize`; an unbounded in-memory upload behind auth is a trivial way to exhaust process memory. `@UploadedFile() file: Express.Multer.File | undefined` (undefined when no file is attached) — throw `BadRequestException` for the missing-file case rather than letting a later `.buffer` access throw a 500. `@types/multer` is a dev-only dependency for the `Express.Multer.File` type (multer itself is already pulled in transitively by `@nestjs/platform-express`). See `PortfolioController.uploadHoldingsCsv` (`apps/api/src/portfolio/portfolio.controller.ts`, `PORTFOLIO_US-2_T-2`) — decodes the buffer to a UTF-8 string and delegates all parsing to the service layer, keeping the controller thin per "Module structure" above.
- The `fileSize` limit itself is `MAX_CSV_UPLOAD_BYTES` (`apps/api/src/common/file-upload.constants.ts`, `1024 * 1024` — 1 MB), a single exported constant every multipart controller imports rather than a private per-controller copy. It started as a private const duplicated in `PortfolioController` and `RecommendedPortfoliosController`; moved here once `MarketDataController.importAssets` became a third consumer (`MARKET_DATA_US-5_T-5`) rather than copy-pasting it a third time.
- PDF text extraction (`AdvisorService.extractPdfText(buffer: Buffer): Promise<string>`, `ADVISOR_US-1_T-1`) uses `pdf-parse@^1.1.4` (the classic `pdf(buffer) => Promise<{ text }>` API), pinned below 2.x deliberately — `pdf-parse@2.x` is an unrelated rewrite (class-based `PDFParse`, native `@napi-rs/canvas` dependency for image/table/screenshot extraction this module never needs). `@types/pdf-parse` is a dev dependency since the package ships no types of its own. Any error `pdf-parse` throws, and text that trims to empty (e.g. a scanned image-only PDF), both become `BadRequestException` — never a 500, never a silently empty result — per spec.md's AC.
- A multipart endpoint that also accepts non-file form fields (e.g. an optional `effectiveDate`/`sourceName` alongside the CSV) declares a second, ordinary `@Body() dto: SomeBodyDto` parameter next to `@UploadedFile()` — `multer` (via `FileInterceptor`) populates `req.body` with the other fields as plain strings before the global `ValidationPipe` runs, so a normal `class-validator` DTO (`@IsOptional() @IsDateString() effectiveDate?: string`, etc.) validates them the same way it would for a JSON body; no special multipart-aware DTO mechanism is needed. See `UploadWalletBodyDto`/`RecommendedPortfoliosController.uploadWallet` (`apps/api/src/recommended-portfolios/dto/upload-wallet-body.dto.ts`, `RECOMMENDED_PORTFOLIOS_US-1_T-6`).
- An endpoint that accepts *either* a multipart file *or* a plain JSON body (no file at all — not just optional extra fields alongside a required file) still only needs one `@Body() dto` + `@UploadedFile() file: Express.Multer.File | undefined` pair: `FileInterceptor` only touches `req.body` when a file is actually attached, so a pure-JSON request with no multipart parts at all validates against the exact same DTO with `file` coming back `undefined`. Routing between the two paths (and rejecting the "neither present" case) belongs in the service, not the DTO — `class-validator` can't express "one of these two inputs is required" against a field (`file`) it never sees. See `UploadReportBodyDto`/`AdvisorController.uploadReport`/`AdvisorService.uploadReport` (`apps/api/src/advisor/dto/upload-report-body.dto.ts`, `apps/api/src/advisor/advisor.controller.ts`, `ADVISOR_US-1_T-2`).

### Scheduled jobs (`@nestjs/schedule`)
- `ScheduleModule.forRoot()` is registered once, in `apps/api/src/app.module.ts`. Individual cron handlers live in a dedicated `<module>.cron.ts` (not inside the module's `.service.ts`), decorated with `@Cron(cronExpression, { name, timeZone })` — always pass `timeZone` explicitly rather than relying on the host clock (UTC in CI/containers). The handler itself just delegates to the module's service (e.g. `MarketDataCron.handleDailyRefresh()` calls `MarketDataService.refreshAllQuotes()`) so the actual logic stays unit-testable without touching the scheduler. See `apps/api/src/market-data/market-data.cron.ts` + `market-data.cron.spec.ts` (added by `MARKET_DATA_US-1_T-4`) — the spec asserts the registered `SchedulerRegistry` `CronJob`'s `cronTime.source`/`cronTime.timeZone` metadata (via a test module importing `ScheduleModule.forRoot()`) rather than advancing wall-clock timers, and separately calls the handler directly to assert delegation.
- When one cron handler fans out to multiple independent upstream syncs (different providers/outage windows), run them via `Promise.allSettled` and log each rejection at `error` level individually — never a sequential `await` inside one `try`, since the first rejection would skip the rest. See `MarketDataCron.handleBenchmarkSync()` (`apps/api/src/market-data/market-data.cron.ts`, `MARKET_DATA_US-3_T-3`), which runs `syncIbovespa`/`syncCdi` this way so a Yahoo Finance outage doesn't also skip the BCB SGS sync (or vice versa); `market-data.cron.spec.ts`'s failure-isolation test stubs one sync to reject and asserts the handler still calls the other, resolves rather than rejecting, and logs the error — the assertion a naive sequential `await` fails.

### Cross-module events (`@nestjs/event-emitter`)
- `EventEmitterModule.forRoot()` is registered once, in `apps/api/src/app.module.ts` alongside `ScheduleModule.forRoot()` — not re-imported by individual feature modules, same convention as `ScheduleModule.forRoot()` (see "Scheduled jobs" above). A module publishing a cross-module signal exports its event name as a string constant next to the emitting service (e.g. `MARKET_DATA_REFRESH_COMPLETED_EVENT` in `apps/api/src/market-data/market-data.service.ts`) and injects `EventEmitter2` to call `.emit(EVENT_NAME, payload)`; the consuming module imports that constant (dependency points the same direction the module dependency table already does — market-data has no import back into portfolio) and listens via a dedicated `<module>.listener.ts` (mirroring `<module>.cron.ts`) with an `@OnEvent(EVENT_NAME)` handler that only delegates into its own service, keeping the actual logic unit-testable without the event bus. See `apps/api/src/portfolio/portfolio.listener.ts` (`PORTFOLIO_US-5_T-2`), which snapshots portfolio value once market-data signals a completed price refresh — and only when the payload reports a nonzero `refreshed` count, since `{ refreshed: 0 }` also covers an upstream outage that must not produce a fabricated flat data point.
- An isolated `*.module.spec.ts`/service spec that needs `EventEmitter2`/`@OnEvent` resolvable at compile time (because the module under test injects `EventEmitter2` directly, or a listener test needs the real decorator registration exercised) adds `EventEmitterModule.forRoot()` to *that test's own* `imports` array rather than to the module file itself — same pattern already established for `ScheduleModule.forRoot()` in `market-data.cron.spec.ts`. See `apps/api/src/market-data/market-data.module.spec.ts` and `apps/api/src/portfolio/portfolio.listener.spec.ts`.

### Shared utilities / models
- `apps/api` depends on `@ai-investment-assistant/shared` (`workspace:*`) — see `apps/api/package.json` and its use in `apps/api/src/health/shared-info.service.ts`. Node resolves the package's `main`/`types` fields to `packages/shared/dist`, so `pnpm --filter @ai-investment-assistant/shared build` must run before the package's exports are usable from `apps/api` (at runtime or type-check). `apps/api/package.json` has a `prebuild` script (`pnpm --filter @ai-investment-assistant/shared build`) so a plain `pnpm --filter api build` — the exact step CI runs — builds `shared` first automatically, without needing the root `pnpm build`. `packages/shared/src/metrics.ts` (below) is consumed the same way.

### Testing
- Jest (NestJS default), spec files colocated next to the code they test (`*.spec.ts`).
- Unit tests mock `PrismaService`. Integration/e2e tests run against a real test Postgres (separate `docker-compose` service, migrated before the suite runs) through `supertest` against an actual Nest application instance — not mocked at the HTTP layer.
- `apps/api/package.json`'s `"jest"` block (standard Nest CLI unit-test config: `rootDir: "src"`, `testRegex: ".*\\.spec\\.ts$"`, `ts-jest` transform) was added by `AUTH_US-1_T-2` — the first task with a real `*.spec.ts` unit test — so plain `pnpm --filter api test` runs colocated unit tests via `ts-jest` instead of falling back to Jest's default Babel transform (which can't parse TS). Kept separate from `apps/api/test/jest-e2e.json`, which only matches `*.e2e-spec.ts`.
- e2e specs live in `apps/api/test/*.e2e-spec.ts`, run via `pnpm --filter api test:e2e` (Jest config at `apps/api/test/jest-e2e.json`, `ts-jest` transform). Build a real app with `Test.createTestingModule({ imports: [AppModule] }).compile()` then `.createNestApplication()` + `.init()` — see `apps/api/test/health.e2e-spec.ts` for the pattern. Endpoints with no DB dependency (like `/health`) need no Postgres/`docker-compose` setup to run this way.
- `main.ts`'s `bootstrap()` (global pipes, `cookie-parser`, CORS) never runs in an e2e spec built this way, since it goes through `Test.createTestingModule` instead of `NestFactory.create`. Any e2e test exercising a cookie-guarded route (see `apps/api/test/auth.e2e-spec.ts`'s `GET /auth/me` cases) must call `configureApp(app)` (see "Cross-cutting `INestApplication` config" above) before `app.init()`, or `req.cookies` stays undefined and every request 401s regardless of the guard's own logic.
- An isolated `<module>.module.spec.ts` that does `Test.createTestingModule({ imports: [SomeFeatureModule] }).compile()` to check DI wiring does **not** get `PrismaModule` for free even though it's `@Global()` — `@Global()` only reaches modules that are actually part of the compiled graph, and a feature module doesn't import `PrismaModule` itself (see "Module structure" above), so a module compiled alone like this never pulls it in. Import `PrismaModule` explicitly in the test's own `imports` array and `.overrideProvider(PrismaService).useValue({} as PrismaService)` before `.compile()` — `overrideProvider` only works on a provider that's already part of the graph, so the explicit import has to come first. See `apps/api/src/market-data/market-data.module.spec.ts` (added when `MARKET_DATA_US-2_T-2` gave `MarketDataService` a `PrismaService` dependency, extended by `MARKET_DATA_US-3_T-1`'s `syncIbovespa` and `MARKET_DATA_US-3_T-2`'s `syncCdi`).
- A full-app e2e spec (`Test.createTestingModule({ imports: [AppModule] })`) that exercises a route which would otherwise fire a real request to an unreliable/rate-limited upstream (e.g. the market-data debug endpoint calling out through `PRICE_PROVIDER`) stubs that dependency with `.overrideProvider(TOKEN).useValue(stub)` on the `TestingModuleBuilder`, before `.compile()` — same mechanism as the isolated-module case above, just applied to the whole app graph instead of one feature module. See `apps/api/test/market-data.e2e-spec.ts` (`MARKET_DATA_US-4_T-2`), which overrides `PRICE_PROVIDER` so its 200 case doesn't depend on live Yahoo Finance.
- When only **one method** of an otherwise-real service needs stubbing (the rest should run for real against the suite's real test Postgres), prefer `jest.spyOn(moduleFixture.get(RealService), 'methodName').mockResolvedValue(...)` after `.compile()`/`.init()` over `.overrideProvider(RealService).useValue(fullStub)` — the latter silently breaks the moment the service grows a second method other code starts calling (a full stub with only `backfillHistory` mocked started throwing `TypeError: ... is not a function` once `PortfolioService` began calling `MarketDataService.findOrCreateAsset` too). `moduleFixture.get(RealService)` returns the same DI singleton the controller under test holds, so the spy is visible everywhere, and the real method (here `findOrCreateAsset`, which only touches the suite's already-real `PrismaService`) keeps exercising real behaviour instead of needing to be reimplemented a second time in the test double. See `apps/api/test/portfolio.e2e-spec.ts` (`RECOMMENDED_PORTFOLIOS_US-1_T-5`).
- Multiple `*.e2e-spec.ts` files run as separate Jest test suites, which Jest parallelizes across worker processes by default — all against the **same** test Postgres (see "Local Postgres" below). An `afterEach`/`afterAll` cleanup must scope its `deleteMany()` to rows that specific suite created (`where: { email: '...' }`, `where: { ticker: { in: [...] } }`) rather than an unscoped `deleteMany()` on a table another suite touches concurrently (e.g. `user`) — an unscoped delete races with, and can wipe rows out from under, an unrelated suite running in parallel. See `apps/api/test/market-data.e2e-spec.ts`'s `afterEach` for the scoped pattern.
- **Scoping is necessary but not sufficient: fixtures must also be unique per suite.** Two suites that each scope correctly but to the *same* value (the same ticker, the same email) still delete each other's rows. Pick fixture values namespaced to the suite — `market-data.e2e-spec.ts` uses `MDTA4` rather than a real-looking `PETR4` that another suite might also reach for.
- Both mistakes above produce the same signature and it is easy to misread: an **intermittent 500** from an endpoint that passes when its suite is run alone (`--testPathPattern`), because the row it depends on was deleted by a parallel suite between two of its own queries. If a suite passes in isolation but fails in the full run, suspect cleanup before suspecting the handler, and re-run the full suite several times — a ~50% flake looks like a pass often enough to be dismissed. This was a real bug: `auth.e2e-spec.ts` (which predates this convention) called an unscoped `prisma.user.deleteMany()` and intermittently broke `portfolio.e2e-spec.ts`'s holding writes on a foreign key.
- Test fixture files live under `apps/api/test/fixtures/<module>/`, with a `README.md` recording why a fixture looks the way it does when its shape (not its values) is the contract — see `apps/api/test/fixtures/recommended-portfolios/` (`RECOMMENDED_PORTFOLIOS_SHARED_T-3`), whose three synthetic wallet CSVs are deliberately odd (differing column order, a tickerless row, `DY_2026` vs `DY_2025`) and are guarded against drift by a spec that only reads files.
- PDF fixtures for `pdf-parse` (see "PDF text extraction" below) must be generated, not hand-trimmed to the smallest possible file: `apps/api/test/fixtures/advisor/README.md` (`ADVISOR_US-1_T-1`) documents and works around a bug in `pdf-parse`'s bundled PDF.js where an otherwise well-formed PDF under ~4KB throws `bad XRef entry`. Both fixtures there pad past that size with a no-op comment after their own `%%EOF`.
- **A spec placed under `apps/api/test/` must be named `*.e2e-spec.ts`, even when it is a plain unit-style test with no DB or Nest app.** `test/jest-e2e.json` is the only config that reaches that directory (the unit config in `package.json` has `rootDir: "src"`), so a `*.spec.ts` there is collected by no runner and looks like coverage that isn't running. See `apps/api/test/fixtures/recommended-portfolios/fixtures.e2e-spec.ts`.
- **Running the api e2e suite locally** mirrors CI's job env: `DATABASE_URL=postgresql://postgres:postgres@localhost:5433/investment_assistant_test?schema=public JWT_SECRET=<any> FRONTEND_URL=http://localhost:3000 ANTHROPIC_API_KEY=<any> AUTH_THROTTLE_LIMIT=1000 pnpm --filter api test:e2e`. `AUTH_THROTTLE_LIMIT=1000` is required: `POST /auth/login`/`/auth/register` are throttled per IP (default 5/min, `AUTH_UI_SHARED_T-5`) and the suites log in from one IP. `ThrottlerModule.forRootAsync` in `apps/api/src/auth/auth.module.ts` reads the env at module init, so a spec can pin its own limit in `beforeAll` before `createTestingModule` (see `apps/api/test/auth-throttle.e2e-spec.ts`); each app instance gets fresh in-memory throttler storage.

## Frontend (`apps/web`)

### Component conventions
- App Router, Server Components by default. Add `'use client'` only on the smallest leaf component that actually needs interactivity/state — never mark a whole page client-side because one child needs it (e.g. in the dashboard, `AdvisorPanel`'s state machine is a client component; the page shell around it isn't).
- Data fetching happens in Server Components via `fetch()` calling the NestJS API directly, with `credentials: 'include'` so the auth cookie is forwarded. Client components receive data as props — they only fetch on their own for a genuinely client-triggered action (e.g. clicking "Generate Portfolio Analysis").
- Shared UI primitives (`Button`, `Card`, `Badge`) live under `apps/web/components/ui/`, one file per component. Added by `DASHBOARD_UI_SHARED_T-4`: `Button` (`variant: 'primary' | 'secondary' | 'ghost'`, `disabled`, `loading` which sets both `disabled` and `aria-busy`, forwards `...rest` to the underlying `<button>`), `Card` (the white rounded surface, optional `title` header slot), `Badge` (`tone: 'positive' | 'negative' | 'neutral'` mapping to `--emerald`/`--red`/`--text-tertiary`). All three are presentational with no `'use client'` of their own — interactivity comes from props supplied by whichever client component renders them.
- `Button` `variant="navy"` (`AUTH_UI_SHARED_T-3`) is the auth-screen submit: `--navy` → `--navy-2` gradient, and while `loading` it renders a 14px `data-testid="button-spinner"` left of the label (navy only; other variants unchanged). Styles inline styles can't express (`:hover` lift, spinner `@keyframes`, `prefers-reduced-motion` opt-out) go in a co-located CSS Module, `apps/web/components/ui/Button.module.css`, not `globals.css`.
- The `(dashboard)` route group's auth guard lives in `apps/web/app/(dashboard)/layout.tsx` (`DASHBOARD_UI_SHARED_T-5`), not `middleware.ts` — middleware can see the `access_token` cookie exists but can't verify its signature without duplicating `JWT_SECRET` into the frontend runtime, so the guard is a real server-side `GET /auth/me` call instead. `getCurrentUser()` reads the cookie via `next/headers`' `cookies()`, forwards it as a `Cookie` header through `apiFetch`, and `redirect('/login')` (`next/navigation`) on **any** failure — no cookie, a `401`, or any other error — so an expired token is indistinguishable from no token at all, which a naive "cookie present?" check gets wrong. It's wrapped in React's `cache()` so a page rendered in the same request (e.g. a header component that wants to greet the user by name) can call the same `getCurrentUser()` again and reuse the result instead of firing a second `GET /auth/me` — `cache()` only dedupes inside an actual React render pass, so it's a no-op (and harmless) when the function is invoked directly in a unit test. Every route in the group inherits the guard by living inside it, so a new page doesn't need to remember to add its own check. Test pattern for this kind of Server Component: call the async component function directly (`await Layout({ children })`) rather than going through Next's bundler, then `render()` the returned element with RTL — see `apps/web/app/(dashboard)/layout.test.tsx`, which mocks `next/headers`, `next/navigation` and the api client via `vi.mock` (shared mock fns declared with `vi.hoisted()`, since `vi.mock` factories are hoisted above plain `const`).
- The `(dashboard)` rail's nav lives in `apps/web/components/layout/SidebarNav.tsx` (`'use client'`, `DATA_SOURCES_US-1_T-1`) and owns `NAV_ITEMS` — add a new dashboard route's link there, not in the layout. It was extracted precisely because `usePathname` is client-only and the layout above must stay a Server Component for its `getCurrentUser` guard; the active link gets `aria-current="page"` plus a `--bg-card-alt`/`--text-primary` pill (others `--text-tertiary`), matched exactly for `/` and by prefix (`href` or `href/…`) for the rest, so a sub-route doesn't also light up Dashboard. Any Server-Component test that renders the dashboard layout must include `usePathname` in its `next/navigation` `vi.mock` factory.
- Form field primitives `TextField` / `PasswordField` (`apps/web/components/ui/TextField.tsx`, `PasswordField.tsx`, `AUTH_UI_SHARED_T-2`): `TextField` takes `id`, `label`, `error?` plus every native input prop. The error renders as `<p id="{id}-error">`, linked via `aria-describedby` with `aria-invalid`. The focus border and ring are Tailwind arbitrary-value classes because inline styles can't express `:focus`. `PasswordField` wraps it with a Show/Hide toggle whose accessible name is "Show password"/"Hide password" (`aria-pressed`), so `getByLabelText('Password', { exact: true })` matches only the input. It holds local `useState` but, like the other primitives, has no `'use client'` of its own.

### Keyboard-operable drop zone (`DropZone` / `FileChip`)
- `DropZone` (`apps/web/components/ui/DropZone.tsx`, `DATA_SOURCES_SHARED_T-6`) is the file-attach primitive for every data-sources import panel — props `{ accept: '.csv' | '.pdf'; label; hint; onFile; onReject }`. It is a real `<button type="button">`, not a `<div>` with a click handler, so it's focusable and in the tab order for free; its accessible name is authored via `aria-label` as `` `${label} — ${format} only` `` because the accepted format has to be spoken, not just shown (spec → Accessibility). `onKeyDown` handles Enter/Space explicitly **and** calls `preventDefault()` — the native button would otherwise also synthesize a click and open the picker twice. Extension matching (`name.toLowerCase().endsWith(accept)`) runs on **both** the drop and the hidden `<input type="file">` `change` path, and a mismatch calls `onReject('{name} is not a CSV file.')` while never calling `onFile` — the `accept` attribute alone is only a filter hint, not enforcement. The drag-over state is exposed as `data-drag-over="true|false"` alongside the `--blue` border/tint, so tests (and any future styling hook) assert an attribute rather than a colour. `FileChip` (`FileChip.tsx`) is its attached-state counterpart; its Replace/× buttons are `aria-label`ed per file name (`Replace holdings.csv`), since several chips can share one screen and a bare "×" says nothing about which file it removes.

### CSV review (`CsvReview`)
- `CsvReview` (`apps/web/components/data-sources/CsvReview.tsx`, `DATA_SOURCES_SHARED_T-7`) renders one parsed CSV's review — summary strip, required-column pills, file-level notices, the full preview table and the issues list — from `{ result: ValidationResult; requiredColumns: string[] }` and nothing else: it is purely presentational, fetches nothing and doesn't know which source is being imported (`ImportPanel` owns that). Counts are **per row, not per issue** (a row with both an error and a warning counts once, as an error), so `Rows = Valid + Warnings + Errors` always holds and the one `aria-live="polite"` region can announce `"10 rows, 2 errors, 1 warning"` — pluralised, zero parts omitted. Status is never colour-only: `StatusPill` always spells Valid/Warning/Error (`data-testid="status-pill"`) and required-column pills pair ✓/✕ with the column name and the word present/missing. The preview renders **every** row inside a `maxHeight: 320` scroll container with `position: sticky` `<th>` headers; empty cells render `—` and a column right-aligns only when every non-empty cell parses via shared `parseBrazilianNumber`.
### Import gate footer (`ImportFooter` / `Banner`)
- `ImportFooter` (`apps/web/components/data-sources/ImportFooter.tsx`, `DATA_SOURCES_SHARED_T-8`) owns the import gate for every data-sources panel: it takes the file's `ValidationResult` (`null` = nothing attached), `skipAvailable`/`skipErrors` + setter, `detailsComplete`/`detailsHint`, a `buttonLabel(rowsToWrite)` builder and the import/cancel handlers, and enables its navy `Button` only when all five gate rules pass, otherwise rendering the **first** unmet rule's verbatim hint (exported as `MISSING_COLUMNS_HINT`/`SKIPPABLE_ERRORS_HINT`/`UNSKIPPABLE_ERRORS_HINT`/`WALLET_DETAILS_HINT`/`REPORT_DETAILS_HINT`). **`skipAvailable` is a prop, never inferred from the validation** — assets/holdings import partially server-side so skipping is real, while the wallet endpoint rejects the whole file, so there the checkbox must not render at all and any row error blocks the import (spec → "Skip rows with errors" only where the server can honour it). `Banner.tsx` beside it is the outcome strip (`role="status"` for success, `role="alert"` for error, ✓/! icon so nothing depends on tint alone).

### Config-driven import panel (`ImportPanel`)
- `ImportPanel` (`apps/web/components/data-sources/ImportPanel.tsx`, `DATA_SOURCES_US-2_T-1`) is the one panel component every data-sources card composes (assets now; holdings/wallet/report in later tasks) — it takes a single `source: ImportPanelSourceConfig` prop and contains **no branch keyed on which source it is**; every source-specific bit (title/description/note, `DropZone` accept + copy, the CSV template source, an optional `detailsSlot`/`detailsComplete`/`detailsHint`, `requiredColumns` + a bound `validate` closure, `skipAvailable`, `buttonLabel`, the import endpoint + optional `extraFormFields()`, and how to read the response into `{ records, errors }` plus a `successMessage`) lives in the config object a small `create*ImportSource(...)` factory builds (see `createAssetsImportSource`, which binds `validateAssetsRows` and `/market-data/assets/import`). Pending state (`file`, its `ValidationResult`, the skip checkbox, and the outcome banner) is kept in one `Record<sourceKey, SourceState>` inside the panel, keyed by `source.key` (`'assets' | 'holdings' | 'wallet:{type}' | 'report'`) — switching which `source` prop is passed in (a card selection) never discards another key's in-progress file, since that key's slot in the record is untouched. Import always posts the **original** `File` object via `apiFetchMultipart` (never a re-serialized/filtered CSV — server-side partial-import is what the skip checkbox maps to), and on success writes `POST /data-sources/imports` (`records` = the response's actual written-row count, `errors` included only when non-empty) before calling the optional `onImported` prop so the page can refresh `GET /data-sources/summary`; on a rejected request the file/validation/skip state for that key is left untouched and a `FAILED` log is written instead (best-effort — a failure logging the failure never masks the original error banner). The success banner's text is `source.successMessage(records)` with `"{n} row(s) with errors skipped."` appended by the panel itself when the response returned any — this composition (not the per-source message builder) is what keeps that sentence identical across sources.

### Dashboard page composition (`(dashboard)/page.tsx`)
- `apps/web/app/(dashboard)/page.tsx` (`DASHBOARD_UI_US-2_T-3`) is the one Server Component every later dashboard-ui wiring task (`US-3_T-2`, `US-4_T-4`, `US-5_T-3`, `US-7_T-5`) extends, not replaces — each adds its own section and its own request(s) to the same page rather than creating a second data-fetching entry point. It calls `getCurrentUser()` (imported from the sibling `(dashboard)/layout.tsx`, see above) for the signed-in user's name, and forwards the same `access_token` cookie itself via its own `cookies()` call for the portfolio endpoints, since `getCurrentUser`'s `cache()` dedupes its own `GET /auth/me` call but doesn't expose the raw cookie value to the page.
- All per-request API calls are issued together via `Promise.allSettled`, not a sequential `await` per endpoint and not a plain `Promise.all` — the dashboard ends up making five calls across the four wiring tasks above, and `allSettled` (unlike `all`) lets one endpoint's rejection degrade just that section instead of failing the whole page. Each result is unwrapped with `result.status === 'fulfilled' ? result.value : <fallback>` — a page-level constant for the empty/fallback shape (e.g. `EMPTY_SUMMARY`), never a re-thrown error.
- **A page-level fetch can have two distinct failure shapes, not just "ok or degraded"** — see `GET /advisor/analysis/latest` in `(dashboard)/page.tsx` (`DASHBOARD_UI_US-7_T-5`). A `404` is the *expected* response for a new user (no analysis generated yet) and must degrade silently, with no error copy anywhere — `AdvisorPanel` just starts in `idle` via `initialAnalysis={undefined}`. Any other rejection (`500`, network failure, etc.) is *unexpected*, still must not take the rest of the page down, but degrades with a visible inline notice (`AdvisorPanel`'s `initialLoadFailed` prop) so the difference between "nothing to show yet" and "something broke" isn't silently erased. Detect the first case with `result.reason instanceof ApiError && result.reason.status === 404` before falling through to the generic "unexpected failure" branch — don't collapse both into one `catch`.
- A derived, no-backend-field value (e.g. the header's `dayChange`, computed from the last two points of `GET /portfolio/performance`'s `series` — see `PortfolioHeader`'s own convention entry) is computed in the page from whichever fetch succeeded, and must independently produce its own `null`/empty fallback when that fetch's data is missing or too short — not assume the fetch it depends on succeeded just because another one did.
- **This page occupies the exact same route (`/`) as the Next.js starter's `apps/web/app/page.tsx` placeholder**, since a route group like `(dashboard)` doesn't appear in the URL. `US-2_T-3` deleted that placeholder (`app/page.tsx` + its colocated `app/page.test.tsx`) as part of standing up the real page — two `page.tsx` files resolving to the same route is a Next.js build error, not a lint warning, so this isn't optional cleanup.

### Inverted auth guard for the `(auth)` route group
- `redirectIfAuthenticated` (`apps/web/app/(auth)/redirect-if-authenticated.ts`, `DASHBOARD_UI_US-1_T-3`) mirrors `(dashboard)/layout.tsx`'s `getCurrentUser` guard above but flips the outcome: same `cookies()` + `GET /auth/me` probe, but `redirect('/')` on **success** (a still-valid session) rather than on failure, and a missing cookie/401/any other error is treated as "not authenticated" and just returns so the page renders its form. Called at the top of both `apps/web/app/(auth)/login/page.tsx` and `.../register/page.tsx` — without it, a signed-in visitor following a stale `/login` bookmark would be offered a form to log into the session they already have. ### Mutation forms feeding a server-rendered list — file upload variant
- The former `HoldingsCsvUpload`/`AddHoldingForm` (holdings page) were removed in `DATA_SOURCES_US-7_T-1`; the multipart clear/disable/`router.refresh()` shape now lives in `ImportPanel` (`apps/web/components/data-sources/ImportPanel.tsx`) — use it as the reference. Its file input is never client-parsed (column resolution is the backend's job) and is disabled while the upload is in flight.
- **A `{ created, updated, errors[] }` response with a non-empty `errors[]` alongside a nonzero `created`/`updated` is a partial success, not a failure state.** Render all three facts together — both count lines and every `errors[]` entry as its own list item — never suppress the counts because errors exist, and never show a scary "upload failed" banner when rows *did* import. Reserve the actual error/alert state for a rejected request (`ApiError`/network failure), which is a different case from a 2xx response that happens to carry row-level errors. Worth checking again for any sibling multipart-upload component (e.g. a future recommended-portfolios wallet upload) that returns a similar partial-success shape — defaulting to an all-or-nothing success/failure UI is an easy, non-obvious way to get this wrong.

### One component, two request-body shapes (file-upload-or-JSON toggle)

### Required select with no default (a guess corrupts data)
- Reference removed: the original example, `RecommendedPortfoliosUpload` (`DASHBOARD_UI_US-7_T-2`), was deleted by `DATA_SOURCES_US-7_T-2`. The pattern stands: a required select starts at `value=""` with no option pre-selected, and submitting it unset is a client-side error that fires no request; never default to the first enum member, because a wrong guess silently files data under the wrong label. The surviving example is the wallet type selector (`WalletTypeSelector`, used by `WalletImportSection` in `apps/web/components/data-sources/`).

### Stale-response guard for a client-fetched "current selection" (range toggles, typeahead, etc.)
- `PerformanceRange` (`apps/web/components/dashboard/PerformanceRange.tsx`, `DASHBOARD_UI_US-4_T-2`) is the `'use client'` boundary around the presentational `PerformanceChart`: it holds the selected `6M`/`1Y`/`ALL` range, is seeded with the page's server-rendered `6M` response via an `initialData` prop (so mount fires **no** fetch — only a range *change* does), and re-fetches `GET /portfolio/performance?range=...&benchmark=...` through `apiFetch` on click. Two requests started close together can resolve **out of order** (a slow `ALL` response landing after a faster, later-clicked `1Y` one), which would otherwise overwrite the chart with data that no longer matches the highlighted button. The fix is a ref (`selectedRangeRef`, not `useState` — reading it must never wait for a re-render) holding whichever range is *currently selected*, set synchronously at click time; each in-flight request closes over the range it was made for and compares that against the ref's current value both on success and on failure before calling `setData`/`setFailedRange`, dropping the update if they've diverged. This is the general shape for any future feature with the same race (a typeahead re-searching per keystroke, any other "reselect before the last request finishes" client fetch) — reach for a ref-tracked "current selection" compared at resolution time, not a boolean `isLoading` flag (which can't tell *which* request finished, only *that* one did) and not `AbortController` alone (still needs the same comparison in the `catch`, since an aborted fetch's rejection has to be told apart from a genuine failure). Relatedly, the button group's busy state uses `aria-disabled` rather than the native `disabled` attribute precisely so a second click *can* interrupt an in-flight first request — a truly disabled button group would make the race impossible to hit rather than guarded against, defeating the point.
- Failure UX for the same component: a rejected fetch leaves the previously rendered series on screen (never blanks the chart) and shows an inline "Retry" affordance that re-fires the same request — losing data the user already had because one request failed is the wrong tradeoff, matching this file's existing "never blank on a transient failure" theme elsewhere (e.g. `AllocationDonut`'s own empty-state handling).
- **A derived sibling that must track the current selection is a child of the client wrapper, not a sibling on the server page.** `DASHBOARD_UI_US-4_T-4` nests `PerformanceMetrics` inside `PerformanceRange` (reading its own `data` state, not the `initialData` prop) rather than rendering `PerformanceMetrics` from `(dashboard)/page.tsx` fed by the same server-fetched `6M` payload — if it were a page-level sibling it would stay frozen on `6M` after a range-toggle click, since the page never re-renders on a client-only state change. `(dashboard)/page.tsx` still owns the one `GET /portfolio/performance?range=6M&benchmark=IBOVESPA` fetch (reused for both the header's `dayChange` derivation and this section's `initialData` — never fetched twice for the same data).

### Auth forms
- **Sign-in and Create account are both `AuthScreen`, not `LoginForm`/`RegisterForm`** — `apps/web/components/auth/LoginForm.tsx` (deleted by `AUTH_UI_US-1_T-3`) and `apps/web/components/auth/RegisterForm.tsx` (deleted by `AUTH_UI_US-2_T-5`) are both gone; `apps/web/app/(auth)/login/page.tsx` and `apps/web/app/(auth)/register/page.tsx` are now server components that do nothing but `await redirectIfAuthenticated()` and render `<AuthScreen startMode="signin" />` / `<AuthScreen startMode="signup" />` respectively (no page-level `<h1>`, no page-level cross-link to the other mode — both live inside `AuthScreen`). Its error mapping is three-way, not two-way (spec → `specs/auth-ui/spec.md` → "Server and network errors"): `ApiError` `401` → one generic "Email or password is incorrect." (an account-enumeration guard — it must never say which of the two was wrong, spec → Security), `ApiError` `429` → "Too many attempts. Please wait a minute and try again." (the per-IP throttle from `AUTH_UI_SHARED_T-5`), anything else (network failure, 500) → "Couldn't reach the server. Please try again." Keep those three branches distinct in any sibling auth form; Create account mode's `409` (rendered on the Email field, not the form alert — see the `AuthScreen` entry below) is the deliberate exception per its own story notes, not a reason to generalize this into a shared error-mapping helper.
- `AuthScreen` (`apps/web/components/auth/AuthScreen.tsx`, `AUTH_UI_US-1_T-1`) is the redesigned two-mode Sign in / Create account screen from `specs/auth-ui/spec.md`; this task implements the `signin` mode's fields and client-side validation only (empty email/password, `isValidEmail` format check — spec → Behavior Notes → Validation) — submit/`apiFetch` wiring and server-error mapping is `AUTH_UI_US-1_T-2`, Create account mode is `AUTH_UI_US-2`, and client-side mode switching without a remount is `AUTH_UI_US-3_T-1`. **Focusing the first invalid field needs `document.getElementById(fieldId)`, not a ref** — `TextField`/`PasswordField` (see "Form field primitives" above) are plain function components with no `forwardRef`, so passing them a `ref` prop silently does nothing (a React dev warning, not a compile error) rather than reaching the underlying `<input>`; each field's `id` is already stable and unique, so `getElementById` is the reliable way to focus a specific field from outside — reuse this for any future field that needs programmatic focus rather than adding `forwardRef` unless a real need for it shows up. Field errors surface two ways at once: inline via each field's own `error` prop, and pooled into one `aria-live="polite"` region (spec → Accessibility) — a test asserting one specific field's error text needs `{ selector: "p" }` to disambiguate from the live region's `<div>`, since with only one field erroring the two elements' text is identical.
- `AuthScreen`'s `signin` submit (`AUTH_UI_US-1_T-2`) layers on top of the above: `handleSubmit` becomes async, guarded by `if (isSubmitting) return;` at its very top per "Disable-and-guard a button that triggers a paid API call" below (the navy submit `Button`'s own `disabled`/`loading` prop is the first layer, but doesn't stop a same-form Enter-key re-submit while a request is in flight) — client validation still runs and `return`s before any request on a failure, exactly as `AUTH_UI_US-1_T-1` left it. On success it posts `{ email: email.trim(), password }` (never the raw untrimmed field value, in case the caller sets it directly rather than through the `<input type="email">`'s own value-sanitization) to `POST /auth/login` via `apiFetch`, then `router.push("/")` **before** `router.refresh()` — both only in the `try`'s success path, matching the ordering rule above. The three-way error mapping (`ApiError` `401`/`429`/anything else, spec → "Server and network errors") renders into one `<p role="alert">` above the submit button; `isSubmitting` always resolves in `finally`, and neither `email`/`password` state is ever cleared on failure. **A test asserting this alert's message can't use `getByRole('alert', { name })`** — the ARIA `alert` role has no "name from content" rule (name is author-only, e.g. `aria-label`), so `getByRole`'s `name` filter silently never matches even once the element is in the DOM; query `findByRole("alert")` first, then assert on `.toHaveTextContent(...)` instead. Also note jsdom's `<input type="email">` applies real value-sanitization (leading/trailing whitespace is stripped when `fireEvent.change` sets `target.value`), so a test that specifically wants to exercise the component's own `.trim()` call (rather than accidentally relying on jsdom already having done it) needs to set the input's `value` property directly via `Object.defineProperty` before firing a bare `fireEvent.change(input)`, bypassing the sanitizer `target.value` would otherwise trigger.

The meter is advisory and never gates submission: an 8-character score-1 password submits. Status mapping in full: signup `409` → Email field, signup `400` → "Check your details and try again.", signin `401` → the generic credentials message, either mode's `429` → the throttle message, everything else → the network message.

### CSS `conic-gradient` donut (`AllocationDonut`)
- `AllocationDonut` (`apps/web/components/dashboard/AllocationDonut.tsx`, `DASHBOARD_UI_US-3_T-1`) is the reuse point the spec calls out — props are exactly `{ title, slices: AllocationSlice[], centerLabel, centerSubLabel }`, nothing sector-specific. It builds a CSS `conic-gradient(...)` by accumulating each slice's `pct` into running `from`/`to` stops using the slice's own `color` (never the array index — see `computeAllocation`'s own doc comment). Three gotchas worth knowing before touching this again: an empty `slices` array must never reach `conic-gradient()` with zero stops (invalid CSS, takes the whole panel down) — render a neutral `var(--border)` ring and an empty-state message instead; the last stop is pinned to exactly `100%` rather than the accumulated float total, since summing `pct` over many slices leaves a hairline gap short of `100%` from floating-point drift; and a single-slice gradient is built as two same-color single-position stops (`color 0%, color 100%`) rather than one double-position stop (`color 0% 100%`) — both are valid CSS and render identically in real browsers, but jsdom's `cssstyle` (used by Vitest/RTL) silently fails to parse the double-position single-stop form and falls back to `background-image: none`, so a test asserting the gradient rendered at all would pass for the wrong reason (or fail) depending on which form is used.

### Sorting rows with a missing sort key
- `HoldingsGrid` (`apps/web/components/dashboard/HoldingsGrid.tsx`, `DASHBOARD_UI_US-5_T-2`) sorts `HoldingWithAsset[]` by market value (`quantity * asset.currentPrice`) descending, but `asset.currentPrice` is nullable — comparing `null` numerically is undefined and can park unpriced rows anywhere, including the top. The fix is a dedicated `marketValueSortKey` that returns `-Infinity` for a `null`-priced holding rather than falling back to `0`: `-Infinity` always loses a descending comparison, so the row lands last regardless of what real (even zero-value) rows exist, whereas `?? 0` would misplace it relative to any genuinely zero-value row. The same shape — an explicit non-numeric sentinel key for "no computable value," not a `?? 0` coercion — applies to any other list sorted by a value that can be legitimately absent.

### Hand-rolled SVG charts
- `PerformanceChart` (`apps/web/components/dashboard/PerformanceChart.tsx`, `DASHBOARD_UI_US-4_T-1`) is the pattern for a hand-rolled SVG line chart with an overlay series (no charting library, spec Non-Goal): map both series' points to `[x, y]` coordinates against **one shared `[min, max]` domain computed across both series combined**, never each series' own min/max — independent scaling makes two lines cross in ways the underlying numbers never did, defeating the point of the overlay. Guard the three degenerate series a naive `(v - min) / (max - min)` mishandles: zero points (empty state, no `<path>`), one point (an explicit flat two-point path spanning the full width, not a zero-length path), and an all-equal series (`max - min === 0`, special-cased to render flat at vertical-center rather than producing `NaN` in `d`, which renders as a silently blank chart, not an error). `vector-effect="non-scaling-stroke"` on every `<path>` since `preserveAspectRatio="none"` otherwise stretches stroke width non-uniformly with the container.

### `Json` columns rendered as arrays — empty state and verbatim values
- `AdvisorAnalysisResult` (`apps/web/components/dashboard/advisor/AdvisorAnalysisResult.tsx`, `DASHBOARD_UI_US-7_T-3`) is the reference for rendering a Prisma `Json` column that's typed as an array in `apps/web/lib/types.ts` (`AdvisorAnalysis.strengths`/`risks`/`recommendations`/`impactMetrics`) but has no compile-time shape guarantee from Prisma itself. Two rules worth keeping consistent wherever this pattern recurs: (1) an **empty array is a legitimate value, not a missing one** — render its own explicit "none identified" state per section rather than letting the section disappear, since a model finding zero risks and a rendering bug both look identical as blank space; (2) a field that is already a **string the model itself wrote** (`impactMetrics[].value`, e.g. `"12.5%"` or `"-0.8%"`) is rendered verbatim — never re-parsed as a number, never has a unit appended, since the model chose its own formatting and reformatting it risks silently changing its meaning. Also note the `score != null` (not `score ||`) guard for a numeric field whose valid range includes `0` — `{score || fallback}` swallows a real `0` as if it were absent.

### Disable-and-guard a button that triggers a paid API call
- `AdvisorPanel` (`apps/web/components/dashboard/advisor/AdvisorPanel.tsx`, `DASHBOARD_UI_US-7_T-4`) owns the `idle` -> `loading` -> `report` | `error` state machine around `POST /advisor/analyze` — every click is a real Claude call, so "can't be triggered twice concurrently" is its own spec AC, not just good manners. ### Wire-format fractions vs. already-scaled percentages
- `GET /portfolio/performance`'s `cagr`/`volatility`/`maxDrawdown`/`vsBenchmarkPct` (`apps/web/lib/types.ts`'s `PerformanceResponse`) are **fractions** straight off `packages/shared/src/metrics.ts` (e.g. `0.123` means `12.3%`) — a consumer must multiply by `100` before appending a `%`. ## Shared package (`packages/shared`)

### Allocation math
- `computeAllocation` (`packages/shared/src/allocation.ts`, `PORTFOLIO_US-3_T-1`) groups `{ label, value }[]` by label (`null` → `"Unclassified"`), returning `{ label, value, pct, color }[]` sorted by `value` descending — the exact shape `GET /portfolio/allocation` returns. `color` is derived from the label via a deterministic string hash into the exported `ALLOCATION_COLOR_PALETTE`, not from the slice's array index — index-based color would reshuffle every label's color across renders since slices are sorted by value. Both `apps/api`'s allocation endpoint and dashboard-ui's `AllocationDonut` should consume this rather than reimplementing grouping/coloring.

### Pure calculation utilities
- `packages/shared/src/metrics.ts` — `cagr`/`volatility`/`maxDrawdown`, each a pure function over a `PortfolioValuePoint[]` (`{ date: Date; value: number }[]`, sorted ascending by date), re-exported from `packages/shared/src/index.ts`. All three return `0` (never `NaN`/`Infinity`/a throw) for a series shorter than two points, so callers can serialize straight to JSON without a null-check. `cagr` divides by the actual elapsed calendar-day span (`/ 365.25`) between the first and last point, not the number of data points — snapshots are weekday-only, so point-counting inflates the result. `maxDrawdown` tracks a running maximum rather than `(max - min) / max`, since the naive formula is wrong whenever the minimum precedes the maximum. `volatility` uses the sample (n-1) standard deviation of daily returns scaled by `√252`. This is the general pattern for any future pure calculation (allocation math, formatters, etc. per `CONVENTIONS.md`'s own top-level "Pure/testable logic ... belongs in `packages/shared`" rule): one file per concern, colocated `*.test.ts`, re-exported from `index.ts`. Added by `PORTFOLIO_US-5_T-1`.
- `packages/shared/src/validation.ts`: `isValidEmail(email)` (`^[^\s@]+@[^\s@]+\.[^\s@]+$`), pure and non-trimming, so callers trim first if they want to. Use it for any client-side email check instead of an inline regex. Added by `AUTH_UI_SHARED_T-1`.
- `scorePassword` (`packages/shared/src/password-strength.ts`, `AUTH_UI_US-2_T-2`) returns `{ score: 0-4, label }` for the advisory strength meter; colours stay in the web component.

### CSV parsing (isomorphic)
- `parseCsv(text)` / `findColumn(columns, name)` (`packages/shared/src/csv/parse-csv.ts`, `DATA_SOURCES_SHARED_T-1`) — a dependency-free, pure CSV reader both `apps/api` importers and the web data-sources preview consume, so a preview can never run different parsing code than the import it promises (`specs/data-sources/spec.md` → "One parser, two callers"). Returns `{ columns, rows }` with quoted fields (commas, newlines, `""` escapes) handled, every header/value trimmed, short rows padded with `""` and extra cells dropped. `columns` keeps the file's **original** header spelling and rows are keyed by exactly those strings — case-insensitive resolution is a separate `findColumn(columns, 'ticker')` step returning the original spelling (or `undefined`), rather than lowercasing the keys, so error messages can quote the file's own header text back to the user.
- `validateAssetsRows` / `validateHoldingsRows` / `validateWalletRows` + `parseBrazilianNumber` + `ASSETS_COLUMNS`/`HOLDINGS_COLUMNS`/`WALLET_COLUMNS` (`packages/shared/src/csv/validators.ts`, `DATA_SOURCES_SHARED_T-2`) — one `{ columns, rows, rowIssues, fileIssues }` validator per CSV source, built on `parseCsv`/`findColumn` above and self-contained duplicates of the enum member lists and `parseBrazilianNumber` (`apps/api` isn't importable from here), so the web preview and the API importers enforce identical rules. `*_COLUMNS` are the required/optional column lists `SHARED_T-9`'s downloadable templates generate from.
- `buildCsvTemplate(source, walletType?)` / `csvTemplateFileName(source, walletType?)` (`packages/shared/src/csv/build-csv-template.ts`, `DATA_SOURCES_SHARED_T-9`) — the header-only CSV template for an import source, generated from `ASSETS_COLUMNS`/`HOLDINGS_COLUMNS`/`WALLET_COLUMNS` (read at call time, never restated) so a template can't list a column the parser rejects; required columns first, then optional, comma-joined on one line. Every generated cell — header names included — goes through the `=`/`+`/`-`/`@` → `'`-prefix escape, so the rule survives a column being renamed later (spec → "Templates and CSV safety"). Apply the same escape to any *other* CSV this app ever generates. The web side is `apps/web/components/data-sources/TemplateDownloadButton.tsx`: a self-contained `'use client'` button (import panels just render it) that builds a `Blob`, downloads it through a temporary anchor appended to `document.body` (Firefox ignores a click on a detached one) and `URL.revokeObjectURL`s the object URL straight after — test such a component by stubbing `URL` via `vi.stubGlobal` and spying on `document.createElement` to capture the anchor's `download`.
- `apps/api/src/market-data/assets-csv.ts`'s `parseAssetsCsv` and `apps/api/src/recommended-portfolios/wallet-csv.ts`'s `parseWalletCsv` (`DATA_SOURCES_SHARED_T-3`) consume `parseCsv`/`findColumn` for splitting/header resolution and `validateAssetsRows`/`validateWalletRows`'s `fileIssues` for the required-column check, replacing their own `csv-parse` calls — same functions the browser preview runs, so a column the preview resolves (including case-insensitively, via `findColumn`) is guaranteed to be the one the server resolves too. `apps/api/src/recommended-portfolios/wallet-validation.ts` already has its own, differently-shaped `validateWalletRows` (whole-row normalisation + all-or-nothing `BadRequestException`) — the shared one is imported only inside `wallet-csv.ts`, never alongside the local one, to avoid a name clash. The holdings parser in `apps/api/src/portfolio/portfolio.service.ts` is **not yet refactored**: it still parses the old positional three-column CSV, pending the header-name Brazilian-format parser from `specs/portfolio/spec.md` (PR #176) — refactoring it to `validateHoldingsRows` before that lands would mean validating a format the server doesn't actually accept.
- `validateHoldingsRows` is positional and mirrors `PortfolioService.importHoldingsCsv` byte-for-byte (`DATA_SOURCES_SHARED_T-11`): it reads `ParsedCsv.rawRows` (true trimmed cells, header excluded, unpadded), ignores header text, uses `Number()`. `apps/api/src/portfolio/holdings-parity.spec.ts` runs one fixture set through both; the server wins on any disagreement, and any change to either side must keep that spec green.

### Testing
- Vitest (`"test": "vitest run"` in `packages/shared/package.json`), specs colocated as `*.test.ts` next to the code they test — same colocation convention as `apps/web`. No `vitest.config.ts` needed here (plain Node/TS, no jsdom/React), unlike `apps/web/vitest.config.ts`.
- `packages/shared/tsconfig.json` (the config `build`/`typecheck` both run via `tsc -p tsconfig.json`) has `"exclude": ["src/**/*.test.ts"]` so test files never end up in `dist/` (which `apps/api`/`apps/web` consume as the package's compiled output) — vitest itself compiles test files on the fly and doesn't need them in `include`. One side effect: `pnpm --filter @ai-investment-assistant/shared typecheck` doesn't typecheck test files as a result; vitest still catches real type errors in them at test-run time.
- `pnpm --filter @ai-investment-assistant/shared test` is the deliverable command, but note pnpm's own recursive/`--filter` run has a special case for the literal script name `test`: if it's missing, `--filter` silently no-ops (exit `0`, no output) instead of erroring, unlike any other script name (which prints `None of the selected packages has a "<name>" script`). To confirm a real "no test script" failure (e.g. before this setup existed), run `pnpm test` directly inside `packages/shared/` instead of through `--filter` from the repo root.

### Local Postgres (docker-compose)
- Root `docker-compose.yml` (`caioq/ai-investment-assistant`) defines two Postgres 16 services: `db` (dev, host port `5432`, db name `investment_assistant`) and `db-test` (test, host port `5433`, db name `investment_assistant_test`) — separate host ports so `db-test` never collides with `db` and integration tests never touch dev data. Both use `postgres`/`postgres` credentials and a `pg_isready` healthcheck. `pnpm db:migrate` (and any future `apps/api` `DATABASE_URL`) targets `db`; the test suite's `DATABASE_URL` targets `db-test`.

### CI (GitHub Actions)
- `.github/workflows/ci.yml` runs on every `push`/`pull_request`: `pnpm install`, `pnpm lint`, `pnpm typecheck`, `pnpm --filter api build`, `pnpm --filter web build`, `pnpm test` (all workspace unit tests), `prisma migrate deploy`, `pnpm --filter api test:e2e`, `playwright install --with-deps chromium`, `pnpm --filter web test:e2e`. Relies on `apps/api` and `apps/web` each having a `prebuild` script that builds `packages/shared` first (see "Shared utilities / models" above), since CI runs `pnpm --filter <app> build` directly rather than the topologically-sorted root `pnpm build`.
- The e2e steps need a real Postgres, so the job declares a `db-test` **service container** mirroring `docker-compose.yml`'s (same image/credentials/database, published on `5433`) — so `DATABASE_URL` is byte-identical locally and in CI. `JWT_SECRET`, `FRONTEND_URL`, and `NEXT_PUBLIC_API_URL` are set as job-level `env`: the API's e2e boots the real `AppModule` (`JwtStrategy` throws `"requires a secret or key"` at bootstrap without the first), and `apps/web`'s Playwright suite's own `webServer` processes need the same values its local `pnpm --filter web test:e2e` run uses, so a CI failure reproduces locally without a translation step. Migrations are applied with `prisma migrate deploy` (not `migrate dev`), which applies committed migrations without prompting or trying to author new ones.
- Test steps run **after** the builds, so `packages/shared/dist` and the generated Prisma client already exist. `apps/api` has a `pretest` script mirroring its `prebuild` (`build shared && prisma generate`) so `pnpm --filter api test` also works standalone from a fresh clone — `apps/api/generated/prisma` is gitignored, so without it the unit suites fail with a misleading `TS2305: Module '"../../generated/prisma/client"' has no exported member 'Holding'`, which reads like broken code rather than a missing build step.
- **`playwright install --with-deps chromium` is required, not optional** (`DASHBOARD_UI_SHARED_T-8`): skipping `--with-deps` is the usual first CI failure for a fresh Playwright setup — the browser binary downloads fine, but its shared libraries are missing on the runner, and the resulting error names a `.so` file rather than the real cause. `apps/web/playwright.config.ts` also sets `workers: 1`/`fullyParallel: false` (the suite shares one fixture user and one database, per `e2e/global-setup.ts` — parallel workers logging in/out as the same user produce flakes that read as real failures) and `retries: process.env.CI ? 1 : 0` (so a genuinely flaky spec surfaces as a visible retry in the report, not a silently-absorbed pass or an outright-blocked good PR). On failure, the CI job uploads `apps/web/playwright-report/` (the HTML report, only generated in CI via the `reporter` config's `process.env.CI` branch — traces are embedded in that report, not a separate artifact) as `playwright-report`.

### Auth
- Every protected controller uses a shared `AuthGuard` (`apps/api/src/auth/auth.guard.ts`) that resolves `req.user.id` from the `access_token` httpOnly cookie. No endpoint outside `AuthModule` accepts a `userId`/`portfolioId` from the client — it always comes from `req.user.id`.
- A `PATCH`/`DELETE` endpoint scoped to `req.user.id` must filter on `(id, userId)` together in the actual DB call, not `id` alone — `AuthGuard` only proves *who* the caller is, not that the row named by `:id` is theirs. Prisma's `update`/`delete` only accept a unique identifier in `where`, so use `updateMany`/`deleteMany({ where: { id, userId } })` instead and check `count`: `0` means "not found or not yours" — return `404` either way (never `403`), so the response can't be used to probe which ids exist for another user. See `PortfolioService.updateHolding` (`apps/api/src/portfolio/portfolio.service.ts`, `PORTFOLIO_US-1_T-3`).
- Signing the JWT and setting the `access_token` cookie is centralized in `AuthService.issueSession(res, user)` (`apps/api/src/auth/auth.service.ts`), configured via `JwtModule.register({ secret: process.env.JWT_SECRET })` in `auth.module.ts`. Both `POST /auth/register` and `POST /auth/login` call this instead of duplicating the sign+`res.cookie(...)` logic (flags: `httpOnly: true, sameSite: 'lax', secure: isProd`, per spec Behavior Notes).

### GitHub issue / project sync
- Repo: `caioq/ai-investment-assistant`. Board: [GitHub Project #2](https://github.com/users/caioq/projects/2) (user-owned, not org). Status field options are (as of this writing) **Backlog**, **Ready**, **In progress**, **In review**, **Done** — confirmed via `gh project field-list 2 --owner caioq --format json`, which shows the live field/option names and IDs; it's user-managed and can be renamed, so re-check if a move ever fails. `move-project-card.sh` (below) matches option names case-insensitively, so callers can write "In Progress"/"In Review" naturally without needing to match the board's actual "In progress"/"In review" casing exactly.
- `/user-stories` (via the `spec-to-stories` skill) creates one GitHub issue per task file (never per story) through the `github` MCP server, and records the issue number in that task's `**GitHub Issue:**` field. Task files remain the source of truth for `/implement` — the issue is a mirror for board visibility, not a second source of status. Issue titles carry the same module-prefixed task ID as the task file (`[AUTH_US-1_T-1] ...`), per "Naming" above.
- **Board sync is owned by callers, not by `spec-implementer`.** `spec-implementer` runs isolated in a worktree with a restricted toolset (no `ToolSearch`, no `issue_write`) and can't reliably reach either mechanism below — it used to document moving the card itself, but that step was unreachable by its own declared tool scope and has been removed. Two things move a task's card, neither of them the agent:
  - **`.claude/commands/implement.md`** moves the card to **In Progress** right after resolving the task file and before launching `spec-implementer` (and the `check-for-work` job in `auto-implement-issues.yml` does the same for the automated path, before the `implement` job runs).
  - **`.github/workflows/link-and-track-pr.yml`** moves the card to **In Review** whenever a PR is opened with a `Closes #<issue>` in its body — regardless of which path opened the PR (local `/implement`, the Actions auto-implement fallback, or a manual PR).
  - Neither path ever closes the issue — that's the `close-on-merge` job in `.github/workflows/link-and-track-pr.yml`, which fires once the referencing PR is merged (a manual step the user does after reviewing the diff) and also moves the card to Done. See "PR ↔ issue linking" below.
- **Why not the `github` MCP server:** `list_issue_fields`/`issue_write`'s `issue_fields` param is GitHub's org-level custom issue-fields feature, not Projects v2 boards — it returns nothing for this repo (personal account, no org) and can't write to a user-owned project. The only real mechanism is the `gh` CLI (`gh project item-edit`, requires a PAT with `project` scope — the default `GITHUB_TOKEN` can't write to a user-owned Projects v2 board) or the equivalent GraphQL mutation. Both callers above use `.github/scripts/move-project-card.sh <issue-number> "<status-option-name>"`, which resolves the project/field/item/option IDs by name at runtime (so a renamed Status option doesn't silently break) and needs `GH_TOKEN` set to a PAT stored as the `PROJECT_BOARD_TOKEN` secret (repo secret for the Actions path; export locally for `/implement`) — same kind of setup as `CLAUDE_CODE_OAUTH_TOKEN` (PR #29).
- GitHub MCP tool names for issue *creation* (used by `/user-stories`) aren't hardcoded here since the server's toolset can change — discover the current ones with `ToolSearch` (e.g. `"github issue"`) before calling them.

### PR ↔ issue linking
- GitHub only registers a `Closes #<issue>` keyword in a PR body as a real linked issue (Development-sidebar link + auto-close-on-merge) when the PR's **base branch is the repo's default branch**. `spec-implementer` often stacks a PR on a dependency's still-open branch (see "Branching, pushing, and PRs per task" below) to keep diffs small — that means a stacked PR's `Closes #<issue>` silently never registers on its own. Confirmed empirically on PR #51/issue #39: unlinked while its base was a dependency's branch, linked immediately once that base was forced to `main`.
- Fix — **the round trip**: `.github/workflows/link-and-track-pr.yml` fires on `pull_request: opened`, extracts the issue number from `Closes #<issue>` in the PR body and, if the base isn't already `main`, moves the base to `main`, waits for the link to register, then **moves the base back to where the author put it**. The link is sticky: once registered it survives the base being restored and survives later pushes to the head branch. Verified end-to-end on a throwaway stacked PR (#90/#89): `closingIssuesReferences` empty while based on the stacked branch, `[89]` once based on `main`, still `[89]` after the stacked base was restored and a new commit pushed. So stacked PRs keep both their issue link and their clean, dependency-only diff.
  - The workflow verifies with `.github/scripts/verify-issue-link.sh <pr> <issue>` (polls `pullRequest.closingIssuesReferences` — registration is asynchronous, a single read races it). If the link doesn't survive the restore, the workflow retargets to `main` and comments on the PR — i.e. it degrades to the old always-retarget behaviour instead of silently losing the link.
- **Closing is explicit, not GitHub's auto-close.** A stacked PR merged into its dependency's branch rather than into `main` never auto-closes the issue, even with a correctly registered link (verified: merged #90 into its stacked base, #89 stayed open). The same workflow's `close-on-merge` job (`pull_request: closed` + `merged`) closes the issue and moves its card to Done, whatever base it merged into. It's idempotent — it checks the issue state first, so a PR that GitHub already auto-closed for is a no-op.
- **There is no API to link a PR to an issue directly — the body keyword is the only mechanism.** Both alternatives are dead ends, confirmed by direct testing against this repo, not by reading docs:
  - `gh issue develop <issue> --branch <existing-branch>` fails with `API returned empty branch name`, regardless of `--base`/`--repo`. It can only *create* a branch, and `spec-implementer` always creates the branch before any PR or linking step runs.
  - The underlying `createLinkedBranch` GraphQL mutation called directly with an existing branch name returns `{"linkedBranch": null}` and creates no link — a silent no-op (that null is what makes `gh` report the empty-name error). Full introspection of GitHub's mutation list shows no other public mutation that attaches a PR to an issue. Don't reintroduce either without re-testing.

### Branching, pushing, and PRs per task
- Branch naming: `task/<MODULE>_US-<N>_T-<T>-<short-title>` (or `task/<MODULE>_SHARED_T-<T>-<short-title>`) — matches the task file's own basename minus `.md`. This is what makes a task's branch/PR discoverable by name alone, which the dependency-branching rule below relies on. Task IDs are module-prefixed (`AUTH_US-1_T-1`, not bare `US-1_T-1`) starting with the `auth` module onward, since `US-1_T-1` alone repeats in every module's `tasks/` directory and becomes ambiguous once flattened into a single GitHub issue list, Project board, or branch namespace shared across all modules — see "Naming" below. `project-setup`'s already-`Done` task files/issues/branches predate this and were left as bare `US-<N>_T-<T>` rather than retroactively renamed.
- Once a task's test is green and its `Status` is set to `Done`, `spec-implementer` commits, pushes its branch, and opens the PR itself via the `github` MCP server (`mcp__github__create_pull_request`, body includes `Closes #<issue>` when the task has a linked issue) — not the `gh` CLI, which isn't installed in this environment. It never merges — merging is always a manual, reviewed step the user does. If the MCP server isn't reachable from the worktree sandbox, the branch still gets pushed and the parent `/implement` session opens the PR afterward instead.
- PR bodies follow `.github/pull_request_template.md`. It's review-oriented: Task (an absolute commit-pinned permalink to the task file, since relative links in a PR body resolve to a compare page) + `Closes #N`, a 1–2 sentence Description, What changed, **Review focus** (files tiered read carefully / skim / skip), **Assumptions / deviations from spec**, Tests mapped to the task's `Test:` field, Evidence, and Stacked on. Everything except Description is in bullets. The API can't attach images, so UI evidence points at the committed Playwright visual baselines (GitHub's rich diff shows before/after), and GIFs are added by hand. PRs opened by hand get the same template pre-filled by GitHub.
- Every task file has a `**Depends on:**` field (`none`, or a comma-separated list of task ids) — this is what `spec-implementer` resolves before picking what to branch off, rather than inferring order from task numbering or story prose:
  - Every listed dependency `Done` and merged (no open PR left on its branch) → branch off `main`. This is the common case and should stay the common case.
  - A listed dependency `Done` but its PR still open → branch off that dependency's branch instead (a stacked PR), so the new task builds on real code rather than a stale `main`.
  - Any listed dependency not yet `Done` → refuse and report blocked; never guess by building on `main` anyway.
- Stacking is a fallback for keeping parallel `/implement` runs moving, not the default habit — merge each task's PR soon after reviewing it so the next task branches off a current `main`. GitHub doesn't auto-rebase a stacked PR after its base is squash-merged, so the longer a stack sits unmerged, the more manual rebasing (`git rebase main` in that task's worktree, then force-push) it'll need later.
- Stacking a PR's base on a dependency's branch is unaffected by issue linking — `spec-implementer` doesn't need to open stacked PRs against `main` to get a working issue link; see "PR ↔ issue linking" above for how that's handled without touching the base branch.

- NestJS files: kebab-case (`market-data.service.ts`), matching Nest CLI defaults.
- React components: PascalCase file and export name (`AllocationDonut.tsx`).
