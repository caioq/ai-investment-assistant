# Conventions

Living map of established patterns and reusable pieces in this codebase. Read this before implementing a task, so architecture doesn't need to be rediscovered by scanning the whole repo. Updated incrementally: whenever a task introduces a new reusable pattern, model, or utility, add a short entry here before marking that task `Done`. Keep entries short — a pointer (file path + one line), not a tutorial. Delete a placeholder heading's `<...>` note once real content exists under it.

## Backend (`apps/api`)

### Module structure
- One module per domain under `apps/api/src/<name>/` (`auth/`, `portfolio/`, `market-data/`, `advisor/`), each with `<name>.module.ts`, `<name>.controller.ts`, `<name>.service.ts`, and a `dto/` subfolder.
- Controllers stay thin: request/response shaping and calling into services only. Business logic (allocation math, prompt building, price aggregation, etc.) lives in services — or in `packages/shared` if it's pure logic the frontend also needs.
- All controller inputs are validated with `class-validator` DTOs behind a single global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true`) registered once in `main.ts` — no ad hoc manual validation inside individual controllers.
- `PrismaService` lives in a global `PrismaModule` (`apps/api/src/prisma/`), injected via constructor DI wherever a service needs DB access. Nothing instantiates `PrismaClient` directly. `PrismaModule` is `@Global()` and exports `PrismaService`, so downstream feature modules just inject it without re-importing `PrismaModule` (except a module with its own standalone `*.module.spec.ts` compiling it in isolation — see "Testing" below). `PrismaService extends PrismaClient`, connecting in `onModuleInit`/disconnecting in `onModuleDestroy`; Prisma 7's generated client requires an explicit driver adapter (no implicit binary engine), so the constructor passes `new PrismaPg({ connectionString: process.env.DATABASE_URL })` (`@prisma/adapter-pg` + `pg`, both added as `apps/api` deps). Since `apps/api/generated/prisma` is gitignored, `apps/api/package.json`'s `prebuild` and `pretest:e2e` scripts both run `prisma generate` first (also exposed standalone as `db:generate`) so a fresh checkout's `build`/`test:e2e` work without a manual step.
- Cross-cutting `INestApplication` config (CORS, global pipes, etc.) that both the real bootstrap and e2e tests need lives in `apps/api/src/configure-app.ts` (`export function configureApp(app: INestApplication)`), called from `main.ts`'s `bootstrap()` right after `NestFactory.create`. e2e specs import `configureApp` from `./configure-app`, never from `../src/main` directly — `main.ts` has a top-level, unconditional `bootstrap()` call, so importing it as a module (even just for a named export) triggers a real `NestFactory.create` + `app.listen()` as a side effect, leaving an open server handle that hangs the Jest process after the suite reports pass. See `apps/api/test/cors.e2e-spec.ts` for the pattern (sets `process.env.FRONTEND_URL` in `beforeAll`, then calls `configureApp(app)` between `createNestApplication()` and `.init()`).
- Prisma schema at `apps/api/prisma/schema.prisma` (datasource/generator only until a module adds models); `apps/api/prisma.config.ts` (Prisma 7) reads `DATABASE_URL` from `apps/api/.env` (gitignored, not committed — matches the `db` service in root `docker-compose.yml`: `postgresql://postgres:postgres@localhost:5432/investment_assistant?schema=public`). Root `pnpm db:migrate` proxies to `apps/api`'s own `db:migrate` script (`prisma migrate dev`), which needs `db` (from `docker-compose.yml`) up first.
- Every Prisma model gets an explicit `@@map("<snake_case_plural>")` so the physical table name is a lowercase plural (`users`, not Prisma's default PascalCase singular `User`) even though the model name itself stays PascalCase singular per Prisma convention. The same `snake_case` rule applies at the column level: any multi-word field gets `@map("snake_case_name")` (e.g. `passwordHash String @map("password_hash")`) — Prisma model field names stay camelCase (matching the rest of the TS stack), but the physical Postgres columns are `snake_case`. This isn't just style: unquoted camelCase identifiers get silently lowercase-folded by Postgres, so raw SQL, `psql`, migrations inspection, and any non-Prisma tool touching the DB directly need exact-case double-quoting to work at all — `snake_case` columns avoid that footgun entirely and match what virtually every non-Prisma SQL/BI tool assumes by default. See `User` in `apps/api/prisma/schema.prisma` (first model in the repo, added by `AUTH_US-1_T-1`) for the pattern.
- When a service needs to depend on an **interface** rather than a concrete implementation (so a future alternate implementation can be swapped in without touching the consumer), TS interfaces don't survive to runtime — Nest DI needs an explicit `Symbol` injection token exported alongside the interface, e.g. `export const PRICE_PROVIDER = Symbol('PRICE_PROVIDER')` next to the `PriceProvider` interface in `apps/api/src/market-data/providers/price-provider.interface.ts`. The module binds a concrete class to that token (`{ provide: PRICE_PROVIDER, useExisting: B3YahooProvider }` in `market-data.module.ts`), and the consumer injects via `@Inject(PRICE_PROVIDER) private readonly x: PriceProvider` rather than naming the concrete class — see `MarketDataService` (`MARKET_DATA_SHARED_T-2`).
- Primary keys are UUIDv7, not autoincrementing integers or `cuid()`: `id String @id @default(uuid(7)) @db.Uuid`. Rationale — sequential integer ids are enumerable/guessable (a real risk once an id can end up in a URL, error message, or JWT payload); UUIDv7 is non-enumerable, globally unique without a DB round-trip, and (unlike random UUIDv4) still time-ordered, so it doesn't fragment the primary-key btree index the way v4 would at scale. `@db.Uuid` stores it as Postgres's native 16-byte `uuid` type (format-validated at the DB level) rather than Prisma's default `TEXT` mapping for `String` ids. Note the id is generated by Prisma Client itself (not a DB-level `DEFAULT`) — there's no `gen_random_uuid()`/`uuidv7()` in the migration SQL, since Postgres only gained a native `uuidv7()` function in v18 and this repo runs Postgres 16 (`docker-compose.yml`). This means a row's `id` only gets populated when inserted through Prisma Client — never via raw SQL/seed scripts that bypass it.

### CSV parsing
- Use `csv-parse` (`csv-parse/sync`'s `parse()`), never `split(',')` — a `name` field or a Brazilian decimal comma silently shifts every column with naive splitting. Parse with `columns: false` (raw string arrays, not the `columns: true` object mode) plus `relax_column_count: true` so a wrong-column-count row doesn't throw and abort the whole parse — `columns: true` + `relax_column_count` silently drops extra columns instead of letting you catch and report a malformed row, whereas array mode lets each row's `.length` be checked explicitly against the expected count. `skip_empty_lines: true` drops a blank trailing line (a text-editor artifact, not a user mistake) without it becoming a reported error. See `PortfolioService.importHoldingsCsv` (`apps/api/src/portfolio/portfolio.service.ts`, `PORTFOLIO_US-2_T-1`) for the pattern: process each data row independently in a loop, collecting per-row failures into an `errors[]` array with a `row N: reason` message rather than throwing on the first bad row or wrapping the batch in one transaction — a malformed row must not roll back the good ones (spec AC-3).

### Scheduled jobs (`@nestjs/schedule`)
- `ScheduleModule.forRoot()` is registered once, in `apps/api/src/app.module.ts`. Individual cron handlers live in a dedicated `<module>.cron.ts` (not inside the module's `.service.ts`), decorated with `@Cron(cronExpression, { name, timeZone })` — always pass `timeZone` explicitly rather than relying on the host clock (UTC in CI/containers). The handler itself just delegates to the module's service (e.g. `MarketDataCron.handleDailyRefresh()` calls `MarketDataService.refreshAllQuotes()`) so the actual logic stays unit-testable without touching the scheduler. See `apps/api/src/market-data/market-data.cron.ts` + `market-data.cron.spec.ts` (added by `MARKET_DATA_US-1_T-4`) — the spec asserts the registered `SchedulerRegistry` `CronJob`'s `cronTime.source`/`cronTime.timeZone` metadata (via a test module importing `ScheduleModule.forRoot()`) rather than advancing wall-clock timers, and separately calls the handler directly to assert delegation.
- When one cron handler fans out to multiple independent upstream syncs (different providers/outage windows), run them via `Promise.allSettled` and log each rejection at `error` level individually — never a sequential `await` inside one `try`, since the first rejection would skip the rest. See `MarketDataCron.handleBenchmarkSync()` (`apps/api/src/market-data/market-data.cron.ts`, `MARKET_DATA_US-3_T-3`), which runs `syncIbovespa`/`syncCdi` this way so a Yahoo Finance outage doesn't also skip the BCB SGS sync (or vice versa); `market-data.cron.spec.ts`'s failure-isolation test stubs one sync to reject and asserts the handler still calls the other, resolves rather than rejecting, and logs the error — the assertion a naive sequential `await` fails.

### Shared utilities / models
- `apps/api` depends on `@ai-investment-assistant/shared` (`workspace:*`) — see `apps/api/package.json` and its use in `apps/api/src/health/shared-info.service.ts`. Node resolves the package's `main`/`types` fields to `packages/shared/dist`, so `pnpm --filter @ai-investment-assistant/shared build` must run before the package's exports are usable from `apps/api` (at runtime or type-check). `apps/api/package.json` has a `prebuild` script (`pnpm --filter @ai-investment-assistant/shared build`) so a plain `pnpm --filter api build` — the exact step CI runs — builds `shared` first automatically, without needing the root `pnpm build`. A future utility (e.g. the CAGR/volatility/drawdown calculations expected at `packages/shared/src/metrics.ts` once the `portfolio` module's performance tasks land) is consumed the same way.

### Testing
- Jest (NestJS default), spec files colocated next to the code they test (`*.spec.ts`).
- Unit tests mock `PrismaService`. Integration/e2e tests run against a real test Postgres (separate `docker-compose` service, migrated before the suite runs) through `supertest` against an actual Nest application instance — not mocked at the HTTP layer.
- `apps/api/package.json`'s `"jest"` block (standard Nest CLI unit-test config: `rootDir: "src"`, `testRegex: ".*\\.spec\\.ts$"`, `ts-jest` transform) was added by `AUTH_US-1_T-2` — the first task with a real `*.spec.ts` unit test — so plain `pnpm --filter api test` runs colocated unit tests via `ts-jest` instead of falling back to Jest's default Babel transform (which can't parse TS). Kept separate from `apps/api/test/jest-e2e.json`, which only matches `*.e2e-spec.ts`.
- e2e specs live in `apps/api/test/*.e2e-spec.ts`, run via `pnpm --filter api test:e2e` (Jest config at `apps/api/test/jest-e2e.json`, `ts-jest` transform). Build a real app with `Test.createTestingModule({ imports: [AppModule] }).compile()` then `.createNestApplication()` + `.init()` — see `apps/api/test/health.e2e-spec.ts` for the pattern. Endpoints with no DB dependency (like `/health`) need no Postgres/`docker-compose` setup to run this way.
- `main.ts`'s `bootstrap()` (global pipes, `cookie-parser`, CORS) never runs in an e2e spec built this way, since it goes through `Test.createTestingModule` instead of `NestFactory.create`. Any e2e test exercising a cookie-guarded route (see `apps/api/test/auth.e2e-spec.ts`'s `GET /auth/me` cases) must call `configureApp(app)` (see "Cross-cutting `INestApplication` config" above) before `app.init()`, or `req.cookies` stays undefined and every request 401s regardless of the guard's own logic.
- An isolated `<module>.module.spec.ts` that does `Test.createTestingModule({ imports: [SomeFeatureModule] }).compile()` to check DI wiring does **not** get `PrismaModule` for free even though it's `@Global()` — `@Global()` only reaches modules that are actually part of the compiled graph, and a feature module doesn't import `PrismaModule` itself (see "Module structure" above), so a module compiled alone like this never pulls it in. Import `PrismaModule` explicitly in the test's own `imports` array and `.overrideProvider(PrismaService).useValue({} as PrismaService)` before `.compile()` — `overrideProvider` only works on a provider that's already part of the graph, so the explicit import has to come first. See `apps/api/src/market-data/market-data.module.spec.ts` (added when `MARKET_DATA_US-2_T-2` gave `MarketDataService` a `PrismaService` dependency, extended by `MARKET_DATA_US-3_T-1`'s `syncIbovespa` and `MARKET_DATA_US-3_T-2`'s `syncCdi`).
- A full-app e2e spec (`Test.createTestingModule({ imports: [AppModule] })`) that exercises a route which would otherwise fire a real request to an unreliable/rate-limited upstream (e.g. the market-data debug endpoint calling out through `PRICE_PROVIDER`) stubs that dependency with `.overrideProvider(TOKEN).useValue(stub)` on the `TestingModuleBuilder`, before `.compile()` — same mechanism as the isolated-module case above, just applied to the whole app graph instead of one feature module. See `apps/api/test/market-data.e2e-spec.ts` (`MARKET_DATA_US-4_T-2`), which overrides `PRICE_PROVIDER` so its 200 case doesn't depend on live Yahoo Finance.
- Multiple `*.e2e-spec.ts` files run as separate Jest test suites, which Jest parallelizes across worker processes by default — all against the **same** test Postgres (see "Local Postgres" below). An `afterEach`/`afterAll` cleanup must scope its `deleteMany()` to rows that specific suite created (`where: { email: '...' }`, `where: { ticker: { in: [...] } }`) rather than an unscoped `deleteMany()` on a table another suite touches concurrently (e.g. `user`) — an unscoped delete races with, and can wipe rows out from under, an unrelated suite running in parallel. See `apps/api/test/market-data.e2e-spec.ts`'s `afterEach` for the scoped pattern.

## Frontend (`apps/web`)

### Component conventions
- App Router, Server Components by default. Add `'use client'` only on the smallest leaf component that actually needs interactivity/state — never mark a whole page client-side because one child needs it (e.g. in the dashboard, `AdvisorPanel`'s state machine is a client component; the page shell around it isn't).
- Data fetching happens in Server Components via `fetch()` calling the NestJS API directly, with `credentials: 'include'` so the auth cookie is forwarded. Client components receive data as props — they only fetch on their own for a genuinely client-triggered action (e.g. clicking "Generate Portfolio Analysis").
- Shared UI primitives (`Button`, `Card`, `Badge`) live under `apps/web/components/ui/`, one file per component.

### Shared utilities
- `apps/web/lib/types.ts` re-exports types from `packages/shared` rather than redefining them — the frontend never declares its own copy of a shape `packages/shared` already owns.
- `apps/web` depends on `@ai-investment-assistant/shared` (`workspace:*`) — see `apps/web/package.json` and its use in `apps/web/app/page.tsx`. Same build-before-consume caveat as `apps/api` (see above): `pnpm --filter @ai-investment-assistant/shared build` must run before the package's exports resolve from `apps/web` (dev server, `next build`, or Vitest) since Node resolves `packages/shared/dist`. Same `prebuild` fix as `apps/api`: `apps/web/package.json`'s `prebuild` script builds `shared` first so `pnpm --filter web build` alone (the CI step) works from a clean checkout.

### Testing
- Vitest + React Testing Library for component tests, colocated `*.test.tsx` next to the component.
- Vitest is configured at `apps/web/vitest.config.ts` (jsdom environment, `@vitejs/plugin-react`) with `apps/web/vitest.setup.ts` loading `@testing-library/jest-dom/vitest` for the `toBeInTheDocument()`-style matchers, and registering `afterEach(() => cleanup())` (from `@testing-library/react`) so multiple `render()` calls across tests in one file don't leak DOM nodes into later assertions (`globals` isn't enabled in the Vitest config, so RTL's auto-cleanup doesn't kick in on its own). Run via `pnpm --filter web test` (`vitest run`).
- Playwright specs live under `apps/web/e2e/`, one spec per critical user flow (not one per page).

## Shared package (`packages/shared`)

### Testing
- Vitest (`"test": "vitest run"` in `packages/shared/package.json`), specs colocated as `*.test.ts` next to the code they test — same colocation convention as `apps/web`. No `vitest.config.ts` needed here (plain Node/TS, no jsdom/React), unlike `apps/web/vitest.config.ts`.
- `packages/shared/tsconfig.json` (the config `build`/`typecheck` both run via `tsc -p tsconfig.json`) has `"exclude": ["src/**/*.test.ts"]` so test files never end up in `dist/` (which `apps/api`/`apps/web` consume as the package's compiled output) — vitest itself compiles test files on the fly and doesn't need them in `include`. One side effect: `pnpm --filter @ai-investment-assistant/shared typecheck` doesn't typecheck test files as a result; vitest still catches real type errors in them at test-run time.
- `pnpm --filter @ai-investment-assistant/shared test` is the deliverable command, but note pnpm's own recursive/`--filter` run has a special case for the literal script name `test`: if it's missing, `--filter` silently no-ops (exit `0`, no output) instead of erroring, unlike any other script name (which prints `None of the selected packages has a "<name>" script`). To confirm a real "no test script" failure (e.g. before this setup existed), run `pnpm test` directly inside `packages/shared/` instead of through `--filter` from the repo root.

## Cross-cutting

### Shared TypeScript/ESLint/Prettier config
- `tsconfig.base.json` (repo root) holds shared strict compiler options with no `module`/`moduleResolution`/`include` opinion — each package's own `tsconfig.json` does `"extends": "../../tsconfig.base.json"` and sets its own `module`/`moduleResolution`/`include`/`outDir` (Nest needs `commonjs`+`node`, Next needs `esnext`+`bundler`).
- `eslint.config.mjs` (repo root, flat config) is the shared ESLint base (`@eslint/js` recommended + `typescript-eslint` recommended + `eslint-config-prettier` to defer style to Prettier). Each package imports and spreads it rather than declaring its own rules: `import rootConfig from '../../eslint.config.mjs'; export default [...rootConfig, /* package overrides */];`
- `.prettierrc.json` / `.prettierignore` (repo root) is the one Prettier config for the whole repo — packages don't declare their own.
- Root `package.json`'s `lint` script runs `eslint .` (self-lints the shared config plus anything at repo root) before delegating to `pnpm -r run lint`, so a broken root config fails fast instead of hiding behind "no projects matched".

### Local Postgres (docker-compose)
- Root `docker-compose.yml` (`caioq/ai-investment-assistant`) defines two Postgres 16 services: `db` (dev, host port `5432`, db name `investment_assistant`) and `db-test` (test, host port `5433`, db name `investment_assistant_test`) — separate host ports so `db-test` never collides with `db` and integration tests never touch dev data. Both use `postgres`/`postgres` credentials and a `pg_isready` healthcheck. `pnpm db:migrate` (and any future `apps/api` `DATABASE_URL`) targets `db`; the test suite's `DATABASE_URL` targets `db-test`.

### CI (GitHub Actions)
- `.github/workflows/ci.yml` runs on every `push`/`pull_request`: `pnpm install`, `pnpm lint`, `pnpm typecheck`, `pnpm --filter api build`, `pnpm --filter web build` — no test step yet (added once the first feature module lands its own tests). Relies on `apps/api` and `apps/web` each having a `prebuild` script that builds `packages/shared` first (see "Shared utilities / models" above), since CI runs `pnpm --filter <app> build` directly rather than the topologically-sorted root `pnpm build`.

### Auth
- Every protected controller uses a shared `AuthGuard` (`apps/api/src/auth/auth.guard.ts`) that resolves `req.user.id` from the `access_token` httpOnly cookie. No endpoint outside `AuthModule` accepts a `userId`/`portfolioId` from the client — it always comes from `req.user.id`.
- A `PATCH`/`DELETE` endpoint scoped to `req.user.id` must filter on `(id, userId)` together in the actual DB call, not `id` alone — `AuthGuard` only proves *who* the caller is, not that the row named by `:id` is theirs. Prisma's `update`/`delete` only accept a unique identifier in `where`, so use `updateMany`/`deleteMany({ where: { id, userId } })` instead and check `count`: `0` means "not found or not yours" — return `404` either way (never `403`), so the response can't be used to probe which ids exist for another user. See `PortfolioService.updateHolding` (`apps/api/src/portfolio/portfolio.service.ts`, `PORTFOLIO_US-1_T-3`).
- Signing the JWT and setting the `access_token` cookie is centralized in `AuthService.issueSession(res, user)` (`apps/api/src/auth/auth.service.ts`), configured via `JwtModule.register({ secret: process.env.JWT_SECRET })` in `auth.module.ts`. Both `POST /auth/register` and `POST /auth/login` call this instead of duplicating the sign+`res.cookie(...)` logic (flags: `httpOnly: true, sameSite: 'lax', secure: isProd`, per spec Behavior Notes).

### GitHub issue / project sync
- Repo: `caioq/ai-investment-assistant`. Board: [GitHub Project #2](https://github.com/users/caioq/projects/2) (user-owned, not org). Status field options are (as of this writing) **Backlog**, **Ready**, **In progress**, **In review**, **Done** — confirmed via `gh project field-list 2 --owner caioq --format json`, which shows the live field/option names and IDs; it's user-managed and can be renamed, so re-check if a move ever fails. `move-project-card.sh` (below) matches option names case-insensitively, so callers can write "In Progress"/"In Review" naturally without needing to match the board's actual "In progress"/"In review" casing exactly.
- `/user-stories` (via the `spec-to-stories` skill) creates one GitHub issue per task file (never per story) through the `github` MCP server, and records the issue number in that task's `**GitHub Issue:**` field. Task files remain the source of truth for `/implement` — the issue is a mirror for board visibility, not a second source of status. Issue titles carry the same module-prefixed task ID as the task file (`[AUTH_US-1_T-1] ...`), per "Naming" above.
- **Board sync is owned by callers, not by `spec-implementer`.** `spec-implementer` runs isolated in a worktree with a restricted toolset (no `ToolSearch`, no `issue_write`) and can't reliably reach either mechanism below — it used to document moving the card itself, but that step was unreachable by its own declared tool scope and has been removed. Two things move a task's card, neither of them the agent:
  - **`.claude/commands/implement.md`** moves the card to **In Progress** right after resolving the task file and before launching `spec-implementer` (and the `check-for-work` job in `auto-implement-issues.yml` does the same for the automated path, before the `implement` job runs).
  - **`.github/workflows/link-and-track-pr.yml`** moves the card to **In Review** whenever a PR is opened with a `Closes #<issue>` in its body — regardless of which path opened the PR (local `/implement`, the Actions auto-implement fallback, or a manual PR).
  - Neither path ever closes the issue — that's the `close-on-merge` job in `.github/workflows/link-and-track-pr.yml`, which fires once the referencing PR is merged (a manual step the user does after reviewing the diff) and also moves the card to Done. See "PR ↔ issue linking" below.
- **Why not the `github` MCP server:** `list_issue_fields`/`issue_write`'s `issue_fields` param is GitHub's org-level custom issue-fields feature, not Projects v2 boards — it returns nothing for this repo (personal account, no org) and can't write to a user-owned project. The only real mechanism is the `gh` CLI (`gh project item-edit`, requires a PAT with `project` scope — the default `GITHUB_TOKEN` can't write to a user-owned Projects v2 board) or the equivalent GraphQL mutation. Both callers above use `.github/scripts/move-project-card.sh <issue-number> "<status-option-name>"`, which resolves the project/field/item/option IDs by name at runtime (so a renamed Status option doesn't silently break) and needs `GH_TOKEN` set to a PAT stored as the `PROJECT_BOARD_TOKEN` secret (repo secret for the Actions path; export locally for `/implement`) — same kind of setup as `CLAUDE_CODE_OAUTH_TOKEN` (PR #29).
- GitHub MCP tool names for issue *creation* (used by `/user-stories`) aren't hardcoded here since the server's toolset can change — discover the current ones with `ToolSearch` (e.g. `"github issue"`) before calling them.

### PR ↔ issue linking
- GitHub only registers a `Closes #<issue>` keyword in a PR body as a real linked issue (Development-sidebar link + auto-close-on-merge) when the PR's **base branch is the repo's default branch**. `spec-implementer` often stacks a PR on a dependency's still-open branch (see "Branching, pushing, and PRs per task" below) to keep diffs small — that means a stacked PR's `Closes #<issue>` silently never registers on its own. Confirmed empirically on PR #51/issue #39: unlinked while its base was a dependency's branch, linked immediately once that base was forced to `main`.
- Fix — **the round trip**: `.github/workflows/link-and-track-pr.yml` fires on `pull_request: opened`, extracts the issue number from `Closes #<issue>` in the PR body and, if the base isn't already `main`, moves the base to `main`, waits for the link to register, then **moves the base back to where the author put it**. The link is sticky: once registered it survives the base being restored and survives later pushes to the head branch. Verified end-to-end on a throwaway stacked PR (#90/#89): `closingIssuesReferences` empty while based on the stacked branch, `[89]` once based on `main`, still `[89]` after the stacked base was restored and a new commit pushed. So stacked PRs keep both their issue link and their clean, dependency-only diff.
  - The workflow verifies with `.github/scripts/verify-issue-link.sh <pr> <issue>` (polls `pullRequest.closingIssuesReferences` — registration is asynchronous, a single read races it). If the link doesn't survive the restore, the workflow retargets to `main` and comments on the PR — i.e. it degrades to the old always-retarget behaviour instead of silently losing the link.
- **Closing is explicit, not GitHub's auto-close.** A stacked PR merged into its dependency's branch rather than into `main` never auto-closes the issue, even with a correctly registered link (verified: merged #90 into its stacked base, #89 stayed open). The same workflow's `close-on-merge` job (`pull_request: closed` + `merged`) closes the issue and moves its card to Done, whatever base it merged into. It's idempotent — it checks the issue state first, so a PR that GitHub already auto-closed for is a no-op.
- **There is no API to link a PR to an issue directly — the body keyword is the only mechanism.** Both alternatives are dead ends, confirmed by direct testing against this repo, not by reading docs:
  - `gh issue develop <issue> --branch <existing-branch>` fails with `API returned empty branch name`, regardless of `--base`/`--repo`. It can only *create* a branch, and `spec-implementer` always creates the branch before any PR or linking step runs.
  - The underlying `createLinkedBranch` GraphQL mutation called directly with an existing branch name returns `{"linkedBranch": null}` and creates no link — a silent no-op (that null is what makes `gh` report the empty-name error). Full introspection of GitHub's mutation list shows no other public mutation that attaches a PR to an issue. Don't reintroduce either without re-testing.

### Branching, pushing, and PRs per task
- Branch naming: `task/<MODULE>_US-<N>_T-<T>-<short-title>` (or `task/<MODULE>_SHARED_T-<T>-<short-title>`) — matches the task file's own basename minus `.md`. This is what makes a task's branch/PR discoverable by name alone, which the dependency-branching rule below relies on. Task IDs are module-prefixed (`AUTH_US-1_T-1`, not bare `US-1_T-1`) starting with the `auth` module onward, since `US-1_T-1` alone repeats in every module's `tasks/` directory and becomes ambiguous once flattened into a single GitHub issue list, Project board, or branch namespace shared across all modules — see "Naming" below. `project-setup`'s already-`Done` task files/issues/branches predate this and were left as bare `US-<N>_T-<T>` rather than retroactively renamed.
- Once a task's test is green and its `Status` is set to `Done`, `spec-implementer` commits, pushes its branch, and opens the PR itself via the `github` MCP server (`mcp__github__create_pull_request`, body includes `Closes #<issue>` when the task has a linked issue) — not the `gh` CLI, which isn't installed in this environment. It never merges — merging is always a manual, reviewed step the user does. If the MCP server isn't reachable from the worktree sandbox, the branch still gets pushed and the parent `/implement` session opens the PR afterward instead.
- Every task file has a `**Depends on:**` field (`none`, or a comma-separated list of task ids) — this is what `spec-implementer` resolves before picking what to branch off, rather than inferring order from task numbering or story prose:
  - Every listed dependency `Done` and merged (no open PR left on its branch) → branch off `main`. This is the common case and should stay the common case.
  - A listed dependency `Done` but its PR still open → branch off that dependency's branch instead (a stacked PR), so the new task builds on real code rather than a stale `main`.
  - Any listed dependency not yet `Done` → refuse and report blocked; never guess by building on `main` anyway.
- Stacking is a fallback for keeping parallel `/implement` runs moving, not the default habit — merge each task's PR soon after reviewing it so the next task branches off a current `main`. GitHub doesn't auto-rebase a stacked PR after its base is squash-merged, so the longer a stack sits unmerged, the more manual rebasing (`git rebase main` in that task's worktree, then force-push) it'll need later.
- Stacking a PR's base on a dependency's branch is unaffected by issue linking — `spec-implementer` doesn't need to open stacked PRs against `main` to get a working issue link; see "PR ↔ issue linking" above for how that's handled without touching the base branch.

### Naming
- NestJS files: kebab-case (`market-data.service.ts`), matching Nest CLI defaults.
- React components: PascalCase file and export name (`AllocationDonut.tsx`).
- Functions/variables: camelCase everywhere (TS on both sides).
- Prisma enum values: SCREAMING_SNAKE_CASE, matching what's already in the specs (`EQUITY`, `DIVIDENDS`, `OVERALL_RECOMMENDED`, ...) — don't introduce a different casing for a new enum.
- Task IDs (starting with the `auth` module onward): module-prefixed — `<MODULE>_US-<N>_T-<T>` / `<MODULE>_SHARED_T-<T>`, e.g. `AUTH_US-1_T-1`, `MARKET_DATA_SHARED_T-1`. `<MODULE>` is the spec's directory name, uppercased with hyphens turned to underscores (`market-data` → `MARKET_DATA`, `recommended-portfolios` → `RECOMMENDED_PORTFOLIOS`). Story IDs (`US-<N>`) stay bare — they're never flattened into a cross-module namespace (no GitHub issue, no branch), only task IDs are. `project-setup` predates this convention and keeps its original bare `US-<N>_T-<T>` IDs; it was not retroactively renamed.
